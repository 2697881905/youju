# 可行性分析前先校验并纠正用户类比前提

## Scenario

用户提出"我们能不能做 X"的可行性/方案类需求，并引用一个现成产品 Y 作为类比（"像 Y 那样"），潜台词是"Y 已经做到了，把 Y 的思路搬到新平台即可"。这类需求中，Y 的**实际技术机制**常被用户误解，类比本身可能不成立。

## Key Signals

- 用户句式："X 平台做不到像 Y 那样……我们能不能做一个类似 Y 的东西？"
- 用户把两个不同层级的技术放在一起类比（如把"同指令集的应用兼容"类比为"跨指令集的系统级转译"）。
- 需求描述中隐含"照搬 Y 即可"的乐观预期，但未说明 Y 的实现机制。
- 用户同时强调"不用写代码，先定位需求、分析技术壁垒"，说明这是调研任务，前提正确性直接决定整篇结论。

## Essence

类比前提的错误会让整篇分析方向跑偏：若顺着错误类比展开，会低估难度、选错参照物、给出无意义的"可行/不可行"结论。正确做法是先拆解并核查前提中的技术断言，判断类比是否成立（同指令集？同内核血统？同 API 层？），前提不成立时**显式纠正并替换参照物**，再重新定义任务本质后展开分析。纠正前提本身就是高价值产出，优先级高于后续壁垒分析。

## Approach

1. **拆解断言**：把用户需求还原为可核查的原子命题（"Y 能在 A 平台运行 B 类软件"→ Y 用的是转译？兼容层？虚拟化？）。
2. **机制核查**：确认 Y 与被类比对象的真实机制差异维度——指令集是否相同、内核血统是否相同、API/运行时层是否可复用。
3. **判定类比是否成立**：若存在本质层级差异，明确给出"前提需纠正"结论，并指出差异的数量级（如差 1~2 个数量级）。
4. **替换参照物**：改用机制上真正可比的参照物（跨指令集转译应对标 Wine/CrossOver/QEMU 等，而非同指令集兼容方案）。
5. **重定义任务本质**：用修正后的前提重新表述"X 到底是什么问题"，再展开壁垒、架构、路径分析。
6. **分级结论**：给出局部可行 / 通用可行的分层评级，避免笼统二值判断。

## Faster Next Time

- 收到"像 Y 一样做 X"的需求时，第一个问题固定为："Y 到底是什么机制，和 X 差几个数量级？"——先答这一问再动笔。
- 把"前提校验"作为可行性分析报告的第一节，而不是塞在附录。
- 在报告中显式区分"用户给定前提"与"核查后前提"，便于评审。

## Applicability Boundaries

- 适用于：可行性评估、技术选型、方案调研、竞品对标类需求，尤其是用户以现有产品作类比的场景。
- 不适用于：用户前提明显正确、或用户已明确要求"不要质疑前提，直接给方案"的场景。
- 纠正前提需要给出机制依据；无依据的否定同样是有害的（应标注为待核实而非直接否定）。
- 不适用于纯实现类任务：此时应通过执行与验证获得事实，而非停留在前提辩论。

## Evidence or Examples

- 本次会话（ses_f21031a16ffeP6M1eugJaHubzE）：用户需求为"鸿蒙电脑无法像鸿蒙手机的卓易通那样转译 Windows 软件，能否做一个 Win 易通"，并要求"仔细定位需求、查阅资料、分析技术壁垒和技术实现"。
- 核查发现的错误前提：手机端"卓易通"实为 **Android 应用兼容**（同指令集、同内核血统），并非 Windows 转译；两者难度差 1~2 个数量级。
- 纠正后结论：Win 易通本质是"在鸿蒙上重建 Windows 用户态运行时"，参照物应为 Wine/CrossOver 而非卓易通；据此给出"局部可行、通用极难"的分级结论，并指出最大壁垒在 Win32/NT API 生态复刻与平台 native/JIT/Vulkan/虚拟化开放度，而非"翻译指令"本身。
