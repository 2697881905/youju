# 多账号分区表的唯一键与每条读写条件必须带分区键，串行写不能替代分区隔离

## Scenario
同一台设备支持游客与多个登录账号切换，业务表用 `user_id`（或 tenant_id/workspace_id）做分区键。写入走统一的串行写通道，并用 `ON CONFLICT REPLACE` 之类 upsert 实现"重复提交即更新"的幂等。

## Key Signals
- 表的主键/唯一键只有业务 id，没有分区键。
- 删除/更新 SQL 的 WHERE 只有业务 id，没有 `user_id`。
- 切账号后，A 的打卡/记账被 B 覆盖、消失，或 `user_id` 被改成 B。
- 代码注释只强调"写串行化/单写通道"，没有提分区条件。
- 跨账号迁移（游客转登录）用一条不带事务的批量 UPDATE。

## Essence
写通道串行化解决的是并发冲突，分区键解决的是归属与可见性，两者正交。唯一约束一旦不含分区键，upsert 的冲突判定就是跨账号的：B 插入相同业务 key 会 REPLACE 掉 A 的行，并把 `user_id` 一并改写。这是隔离性缺陷，加锁、排队、串行写都无法修复；只有把分区键纳入唯一约束和每一条读写条件才能修。

## Approach
1. 所有按账号隔离的表，主键/唯一约束都加入分区键：`PRIMARY KEY (user_id, trip_id, activity_id)` 或等价的独立 UNIQUE。
2. 所有 SELECT/UPDATE/DELETE 的 WHERE 都带分区键；更新/删除以 `业务 id + user_id` 联合定位。
3. upsert 的冲突目标必须与新唯一键一致；`ON CONFLICT REPLACE` 只用于"同一分区内幂等"。
4. 跨账号数据迁移单独用一个事务批量 UPDATE `user_id`，并校验影响行数与预期一致。
5. 测试用例：A 写入 → 切 B 写同业务 key → 切回 A，断言 A 的数据仍在、`user_id` 未被改写、B 的记录独立存在。
6. 改主键/唯一约束视为 schema 变更：新装库与旧库升级两条路径都要重建约束并分别验证（见 `2026-11-01-schema-migration-dual-path-verification`）；删除或重建导致的引用完整性另按 `2026-11-01-manual-cascade-and-orphan-evidence` 处理。

## Faster Next Time
- 审查多账号功能，第一步 grep 建表语句里的 `PRIMARY KEY`/`UNIQUE`，看是否含分区键。
- 第二步 grep 所有 `DELETE`/`UPDATE`，看 WHERE 是否含分区键。
- "单写通道/串行化"的注释不能当作隔离性证明；隔离性要看约束与条件。
- 公共种子表（全员共享、无归属）不要加 `user_id`，否则会被无谓分区。
- 验证约束是否真的生效，用 `PRAGMA index_list(<table>)` / `PRAGMA table_info(<table>)` 读实际索引与主键，而不是只读建表 SQL。

## Applicability Boundaries
- 适用：单库多分区（user_id/tenant_id/workspace_id）且存在 upsert 的本地库或服务端表。
- 不适用：一账号一库/一文件，物理隔离已经保证；或数据本身就是全局共享的公共表。
- 若引入服务端多租户，还需在查询层强制注入 tenant 条件（ORM 拦截器/行级安全），不能只靠每个调用方自觉。

## Evidence or Examples
- 反例：`checkin` 主键仅 `(trip_id, activity_id)`，不含 `user_id`：`entry/src/main/ets/data/DatabaseHelper.ets:90-93`；写入用 `ON_CONFLICT_REPLACE`：`data/CheckinDao.ets:43`，存在跨账号覆盖风险。
