# 让模型只做选择，硬约束算术留在端侧确定性纯函数

## Scenario
"跳过某一站后重排今日剩余行程"这类功能有三种实现：全部交给 LLM 生成新行程；全部用本地规则硬算；混合。全 LLM 贵、慢、同一输入两次结果不同，还可能凭空丢站；全本地又无法理解「哪个更值得保留」。实际采用混合：模型只决定语义取舍，时间算术全部本地确定性完成。

## Key Signals
- 同一请求两次返回不同的 keep 集合或不同的停顿时长。
- 模型给出的 keep 数量与剩余站数量不一致、ID 重复、dwell 超出合理区间、出现未知字段。
- 落库后出现时间重叠、活动结束越过日终、已预约/交通节点被挪动。
- 重排失败时用户看到行程变少（丢站）——这是最严重的一条。

## Essence
把问题的两半切开：**需要语义判断的（保留谁、每站停多久、空档放哪）交给模型；必须正确的（时间线不重叠、不越日终、锚点不动、不丢站）交给确定性代码**。模型输出必须被当作"不可信输入"，先过整份守卫再进入计算，且守卫是拒绝而非修修补补。

## Approach
1. 定义窄契约：请求/响应只交换必要字段（keep / dwell / freeBlocks / note），带 `schemaVersion` 与边界常量（停留 15–240、free 块 ≤3 且 15–480、keep ≤20、note ≤200）。
2. 端侧守卫 `accept()`：版本匹配、keep 与"剩余站"等长且 ID 不重复、dwell 为区间内整数、note 截断/拒绝——不合格整份丢弃走兜底，不做局部修补（局部修补等于替模型猜）。
3. 确定性排程：先用锚点占位（交通/住宿/已预约/带时刻的餐次），其余站逐站加通勤后向后 settle 避让锚点与已占时段；消费 freeBlock 空档；越过日终不强行塞入，标记「待调整」并停止。
4. 兜底绝不丢站：整体顺延"被跳过时长"，有冲突再整体后移；仍不合法则**恢复原时间并全部标「待调整」**，把问题显式交给用户，而不是悄悄删掉站点。
5. 落库前第二次校验（ID 集合、餐次、锚点未动、无重叠、未改站的时间未变），失败则拒绝保存。
6. 撤销：改动前 `cloneDay` 深拷贝快照，保存成功后置为单层内存快照；撤销即写回并落库。明确声明只支持单层、进程内、重启/换行程失效，不做多级撤销也不上数据库 CAS。
7. 被跳过项原地改写而不是删除：id 不变，改成"休息/无需预约/空闲/已跳过"，清坐标与地址——保留可撤销锚点。

## Faster Next Time
- 评审时先找一句判据：「LLM 的输出是否被直接写入持久层」。是则先补守卫，不要先调 prompt。
- 用三个必测用例代替长清单：①keep 缺站/多站/重复 ID；②排到日终边界与跨日；③同一输入跑两次结果完全一致且不丢站。
- 把模型可影响的量限制成"枚举 + 数值区间"，任何自由文本（reason/note）都不参与算术。
- 兜底分支优先写"恢复原状 + 显式提示"，它比"尽力而为地重排"便宜且可解释。

## Applicability Boundaries
- 适用：有硬约束的领域（时间线、金额、坐标、库存）需要模型参与取舍时。
- 不适用：输出本身没有客观正确性（文案改写、命名建议）、或模型不可用的离线场景（此时应整体退化为规则路径）。
- 该模式的成本是"两套逻辑 + 一轮校验"；若领域约束极弱（只是重排序展示），直接本地规则即可，不必引入模型与契约层。
