# skip-worktree 只防误提交，不构成密钥隔离边界

## Scenario
客户端联调阶段需要在配置常量里填真实的 API Key 与端点地址。为了"不把密钥提交进仓库"，常见做法是执行 `git update-index --skip-worktree <file>`，让 `git status` 看不到该文件的本地修改。团队成员和评审者往往据此认为密钥已被隔离。

## Key Signals
- `git ls-files -v` 中该文件前缀是 `S`（skip-worktree），`git status` 对该文件永远"干净"。
- 换机器、重新 clone、CI checkout 后，该文件回到仓库版本（通常是空串），功能"莫名不可用"。
- `git add -f <file>`、`git checkout -- <file>`、`git stash`、部分 IDE 的提交操作会绕过该标记，把明文带进暂存区或历史。
- 构建产物（HAP / APK / IPA / js bundle / 前端静态资源）里能用 `strings`、`grep` 或反编译工具直接搜到密钥字符串。
- 仓库 HEAD 版本是空串、`git log -S` 搜不到密钥，于是被判定"没有泄露"——但本地工作区和安装包里的明文仍然存在。

## Essence
`skip-worktree` 是**本地索引标记**，作用仅是改变当前工作区对工作树的比较行为。它既不是 `.gitignore`，也不是加密，更**不随仓库传播**：它只影响执行过这条命令的那一份克隆。因此它只能降低"手滑提交"的概率，无法提供任何机密性保证。而客户端应用里的密钥最终必然出现在可分发的产物中——这是分发问题，不是配置问题。

## Approach
1. 默认方案：密钥不落源码。改用系统凭据存储（HarmonyOS `@ohos.security.asset` / `preferences` 加密方案 / iOS Keychain / Android Keystore），或由服务端下发短期 token；构建期通过 CI Secret 注入而不是写文件。
2. 只能临时落源码过渡时，把配置位保留为**可提交的空串默认值**，真值只存在于本地工作区；同时使用 `--skip-worktree` 仅作降低误提交概率的补充手段，而非安全措施。
3. 立刻建立可见性检查：
   - `git ls-files -v | grep '^S'`（macOS / Linux bash）列出所有被 skip 的文件，逐个人工确认；
   - `git log -S '<密钥前几位>' --all` 确认历史中确实没有；
   - `git status --ignored` 与 `git diff HEAD -- <config>` 检查本地是否仍有待提交明文。
4. 在评审/CI 加断言：配置文件中密钥字段必须为空串，出现非空值即失败。
5. 发布前 checklist 固定三项：**迁移**（明文位迁入系统凭据存储）、**撤销**（删掉明文常量并解除 skip 标记）、**轮换**（只要明文曾进入过任何构建产物或他人机器，就当作已泄露并换密钥）。
6. 用 `git update-index --no-skip-worktree <file>` 恢复标记，避免长期遗留"看不见的本地改动"。

## Faster Next Time
- 看到 `S` 标记就当"**还没解决**"，而不是"已经隔离"。
- 评审第一问：这个值会不会出现在构建产物里？会，就不是版本控制问题，而是密钥分发问题，必须换存储方案。
- 交接/换机时把 `git ls-files -v | grep '^S'` 当常规自检，能提前发现"克隆后配置为空"这类环境差异。

## Applicability Boundaries
- 适用：任何把配置（密钥、端点、签名口令、私有 token）写进代码仓库的客户端项目；Android / iOS / HarmonyOS / 前端 SPA 同样成立。
- 不适用：完全运行于服务端、密钥从不下发到客户端且仓库访问已受控的场景——即便如此，明文入库仍应避免。
- 平台差异：`--skip-worktree` 的行为在 Git 2.x 各版本基本一致；Windows PowerShell 下 `grep` 需换成 `Select-String`。

## Evidence or Examples
- 配置文件的注释已明确承认这是过渡方案：`entry/src/main/ets/common/config/ApiConfig.ets:19-26` 要求开发期把真值写进本文件并执行 `git update-index --skip-worktree ...`，同时注明"上架前必须迁进系统凭据存储并撤掉本明文位"。
- 本次会话核对结果：`git ls-files` 对该文件输出前缀 `S`；HEAD 提交版本中 `BASE_URL` / `API_KEY` / `REPLAN_TOKEN` 均为空串（`ApiConfig.ets:81,83,91`），说明密钥未进入提交历史。
- 同时本地工作区的 `API_KEY` 已填入真实 `sk-` 前缀密钥——即"历史干净"与"当前明文存在"两件事同时为真，正是该模式最典型的误导点。
- 反例参照：项目对签名配置也用了同一套 skip-worktree 口径，说明这是团队级习惯而非单点疏忽。
