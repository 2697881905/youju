# 文档即契约但会漂移——需要文档随代码校验机制

## Scenario

项目将 `ARCHITECTURE.md` 作为目录职责与依赖方向的"单一事实源"，要求任何结构变更须先更新该文件。代码审查时以此文件为尺子判断分层是否合规。但随着迭代推进，代码与文档逐渐脱节，审查者拿着过时的尺子做判断。

## Key Signals

1. `ARCHITECTURE.md:19` 声明 `utils/` 禁止依赖 `model/`，但实际代码中有 15 处 `utils/*` 直接 import `model/*`（如 `utils/PlanAutoPick.ets:11-13`、`utils/TripEnrich.ets:12-13`、`utils/DayLoad.ets:15`、`utils/MapStops.ets:9-11` 等）。
2. `DatabaseHelper.ets:10` 注释写"表结构（v8）"，但实际 `DB_VERSION = 9`（`:35`），注释滞后一个版本。
3. `TripSignals.ets:5` 的注释与"依赖外部 currentKey"的实现不符。
4. 这些漂移不是一次性事件——每次代码改了但文档没同步更新，就会积累一处漂移。

## Essence

文档作为契约的前提是**文档与代码始终一致**。但没有任何机制保证这一点——文档更新靠人工纪律，代码更新靠功能驱动，两者的更新频率和驱动力完全不同。结果是：文档越写越像"历史记录"而非"当前契约"，审查者拿错尺子做判断，新成员按过时约束写代码。

**根本解法不是"更严格的纪律"，而是"文档随代码校验的自动化机制"**——让代码与文档的不一致在 CI 中自动报红。

## Approach

1. **依赖方向校验脚本**：写一个脚本，解析 `ARCHITECTURE.md` 中的依赖规则表（目录 → 允许依赖 → 禁止依赖），然后扫描代码中的 `import` 语句，检查是否有违反。任何违反都报红。
2. **版本号一致性校验**：在 CI 中检查代码注释中的版本号（如"表结构（v8）"）是否与实际常量（`DB_VERSION = 9`）一致。不一致则报红。
3. **文档更新 checklist**：在 PR 模板中加入"本次改动是否涉及目录结构/依赖方向/版本号变更？如是，是否已更新 ARCHITECTURE.md？"
4. **定期审计**：每月运行一次全量文档-代码一致性审计，输出漂移清单。

## Faster Next Time

- 新建项目时，同步写依赖方向校验脚本，不要等漂移积累后再补。
- ARCHITECTURE.md 中的每条规则都应该是机器可验证的——如果一条规则无法用脚本检查，它就不是有效契约，只是建议。
- 版本号注释不要手写，改为从常量自动生成（如 `// 表结构 v${DB_VERSION}` 在构建时替换）。

## Applicability Boundaries

- **适用**：所有将文档作为架构契约或单一事实源的项目，尤其是分层依赖约束、API 契约、版本号等容易随迭代漂移的场景。
- **不适用**：文档仅作为设计参考而非强制约束的项目；文档与代码天然同步的场景（如文档从代码自动生成）。

## Evidence or Examples

- `ARCHITECTURE.md:19` 声明 utils 禁止依赖 model，但 `utils/PlanAutoPick.ets:11-13`、`TripEnrich.ets:12-13`、`DayLoad.ets:15`、`MapStops.ets:9-11`、`TripReview.ets:12`、`CategoryStyle.ets:11`、`TimeText.ets:9`、`CategoryBudget.ets:9`、`MapCityMapper.ets:13-14`、`IcsBuilder.ets:14,16`、`TripIntentParser.ets:11` 共 15 处违反。
- `DatabaseHelper.ets:10` 注释"表结构（v8）" vs `:35` 实际 `DB_VERSION = 9`。
- `TripSignals.ets:5` 注释与实现不符。
