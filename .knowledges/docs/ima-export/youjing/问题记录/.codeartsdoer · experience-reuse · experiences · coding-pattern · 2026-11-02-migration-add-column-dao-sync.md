# 数据库迁移加列后必须同步更新 DAO 读写与模型字段——否则列存在但端上不可用

## Scenario

使用版本号驱动迁移的数据库应用中，`onUpgrade` 里通过 `ALTER TABLE ADD COLUMN` 给已有表加列是常见操作。但迁移只负责改表结构，如果 DAO 层的 save/load 方法和模型定义没有同步更新，新加的列在端上完全不可读写——列存在于数据库中，但没有任何代码路径会写入或读取它。

更严重的是，如果 DAO 的 save 方法使用 "先 delete 再 insert" 模式（而非 UPDATE），未写入的列会在每次保存时被清空为默认值。即使其他途径（如 BFF 同步）设置了该列的值，一次本地编辑保存就会让它丢失。

## Key Signals

- `ALTER TABLE ADD COLUMN` 已在迁移中执行，但 grep 该列名在 DAO 文件中无命中
- 模型定义（interface/class）中没有该列对应的字段
- save 方法使用 delete + insert 模式，insert 的 ValuesBucket 不包含该列
- load 方法的行映射（resultSet → model）不读取该列
- 列在数据库中存在但端上完全不可读写——等于迁移做了无用功

## Essence

迁移加列是一个跨三层操作：**Schema 层**（ALTER TABLE）→ **DAO 层**（save/load 的读写逻辑）→ **模型层**（interface/class 的字段定义）。只改 Schema 层而不同步 DAO 和模型层，是最常见的迁移不完整 bug。

关键约束：
1. **delete + insert 模式的隐性数据丢失**：如果 save 方法先 delete 整行再 insert，未包含在 insert ValuesBucket 中的列会被重置为默认值。这不是 UPDATE 的部分更新语义——delete + insert 是全量覆盖。
2. **模型层缺失导致全链路断裂**：即使 DAO 层读写该列，如果模型 interface 没有对应字段，数据从数据库读出后无处存放，从 UI 传入时无字段可承载。

## Approach

迁移加列的完整 checklist（每一条都必须验证）：

1. **Schema 层**：`ALTER TABLE ADD COLUMN` 在 `onUpgrade` 中正确执行（已有经验覆盖：累积式 `if (oldVersion < N)`、await DDL、CREATE TABLE 不重复定义）
2. **模型层**：在对应的 interface/class 中添加该列的字段定义
3. **DAO save 层**：在 insert 的 ValuesBucket 中添加该列的写入
4. **DAO load 层**：在 resultSet → model 的行映射中添加该列的读取
5. **验证**：grep 列名，确认在迁移、模型、DAO save、DAO load 四处都有命中

## Faster Next Time

- **grep 验证法**：迁移加列后，立即 grep 新列名，确认在以下四处都有命中：
  - `DatabaseHelper`（迁移定义）
  - `Trip` / 对应 model 文件（字段定义）
  - `TripDao.saveTrip` 或对应 save 方法（ValuesBucket 写入）
  - `TripDao.loadTrip` 或对应 load 方法（resultSet 读取）
- **delete + insert 审查**：如果 DAO 使用 delete + insert 模式，必须确认 insert 的 ValuesBucket 包含所有业务列，否则未包含的列每次保存都会被清空
- **迁移 PR 审查清单**：任何包含 `ALTER TABLE ADD COLUMN` 的 PR，审查者必须检查 DAO 和模型是否同步更新

## Applicability Boundaries

- 适用于：所有使用 ALTER TABLE ADD COLUMN 的数据库迁移
- 适用于：所有使用 delete + insert 模式的 DAO（比 UPDATE 更容易丢失未写入的列）
- 不适用于：纯查询视图列（不需要端上写入的列只需在 load 中读取即可）
- 不适用于：使用 ORM 框架自动映射的项目（框架会自动同步列与字段）

## Evidence or Examples

HarmonyProject2 项目中 v10 迁移加 `pass_id` 列的案例：

1. **Schema 层已加列**：`DatabaseHelper.ets:150-151` — `ALTER TABLE trip ADD COLUMN pass_id TEXT NOT NULL DEFAULT ''`
2. **模型层未同步**：`Trip.ets:115-133` — Trip interface 没有 `pass_id` 字段
3. **DAO save 未写入**：`TripDao.ets:56-63` — `tripRow` ValuesBucket 不包含 `pass_id`
4. **DAO load 未读取**：`TripDao.ets:119-135` — 行映射不读取 `pass_id` 列
5. **delete + insert 导致数据丢失**：`TripDao.saveTrip` 先 `deleteRows` 再 insert，如果 BFF 同步设置了 pass_id，本地编辑保存后 pass_id 会被清空为默认空串

结果：v10 迁移加了 `pass_id` 列，但端上完全不可用，且存在数据丢失风险。严重程度：严重。
