# 库结构迁移要同时验证全新装库与跨级升级两条路径 且 DDL 必须等待完成后再写版本号

## Scenario
本地数据库随版本持续加表、加列（从 v1 演进到 v9）。用户群同时包含两类：全新安装（直接执行最新 CREATE TABLE）和从任意旧版本升级（只执行 onUpgrade 里的增量脚本）。两条路径共用同一份 schema 语义，但执行路径完全不同。

## Key Signals
- 全新安装的库第一次打开就报 `duplicate column name`：建表语句里已有该列，迁移脚本又 `ALTER TABLE ADD` 了一次。
- 迁移后表结构缺表或缺列，但版本号已经是新版本，重启也不再迁移。
- 迁移失败没有任何日志或异常向上抛出，因为 DDL 的 Promise 没有被 await。
- 版本判断写成 `if (oldVersion === N)`，从 v1 直接升到 v4 时跳过中间步骤。
- 文件头注释的表结构版本（如 v8）与常量 `DB_VERSION`（如 9）不一致，说明注释已滞后于代码。

## Essence
"建表"和"迁移"是同一份 schema 的两条写入路径，任何列/表在两条路径里被重复定义，全新库就必然在迁移阶段撞车。更危险的是 DDL 的异步契约：`executeSql` 类接口返回 Promise，不 await 就等于把失败丢进未处理拒绝，而紧接着写 `store.version = 新版本` 又把"可重试的失败"固化成"永久错误状态"。迁移的正确性等于"DDL 全部成功"与"版本号写入"的原子顺序，而不是"脚本写了就算"。

## Approach
1. 建立单一 schema 事实源：建表语句与增量迁移不得重复定义同一列；若保留全量建表，则增量脚本必须先判断列是否存在（`PRAGMA table_info`）或只对老库执行。
2. 版本判断一律用累积式 `if (oldVersion < N)`，不用 `=== N`，保证任意 old→new 逐级补齐。
3. 所有 DDL 调用 await（或统一用事务内的同步 API），并在同一事务里按顺序执行；全部成功后才 `commit` 并写版本号。
4. 迁移失败时 rollBack 且不写版本号，让下次启动重试；catch 里必须记录具体是哪条 DDL 失败。
5. 用两个测试库验证同一套代码：空库直接建到最新版；v1 老库逐级升到最新版。断言表、列、索引、样例数据都在。
6. 定期核对文件头表结构注释与 `DB_VERSION` 常量，避免注释滞后误导下一个人。
7. 迁移若涉及主键/唯一约束或删除语义，结构验证之后还要复核数据语义：唯一键是否含分区键（见 `2026-11-01-partition-key-in-unique-constraint`）、子表与证据行是否留下孤儿（见 `2026-11-01-manual-cascade-and-orphan-evidence`）。结构升版成功不等于隔离性与引用完整性仍然成立。

## Faster Next Time
- 审查迁移先做三件事：grep `ALTER TABLE` 与 `CREATE TABLE` 求列名交集；grep `executeSql` 看是否 await；看版本号写入是否在 DDL 之后。
- 只要看到 `duplicate column`，优先怀疑"全量建表 + 增量 ALTER"双份定义，而不是数据本身。
- 看到 `=== N` 的版本判断，直接判定跨级升级会漏步骤。
- 迁移后没有任何报错但结构不对，先查异步 API 是否被静默丢弃。

## Applicability Boundaries
- 适用：SQLite/RDB 等自管理版本号的本地库，尤其是手写迁移脚本而非 ORM 自动迁移的项目。
- 不适用：纯 ORM 声明式自动迁移（框架内部已处理双路径）、或首个版本尚未发布、没有历史库需要升级的场景。
- 若引入声明式 schema diff 工具，可简化列存在性判断，但"DDL 成功后再写版本号"这一条仍成立。
- 约束变更（重建表并拷数据）比加列风险高得多：老数据可能违反新唯一键，必须在迁移内显式去重或报错回滚，而不是让建约束静默失败。

## Evidence or Examples
- 版本与注释不一致：`entry/src/main/ets/data/DatabaseHelper.ets:35`（`DB_VERSION = 9`）对比 `:10`（表结构写 v8）。
- 双份定义：`trip.user_id` 已存在于建表 `:43`，又由 v2 的 ALTER 添加 `:136` / `:222`；`meal.time` `:60` vs `:116` / `:235`；`spot.confidence` `:71` vs `:108` / `:232`。
- 累积式迁移写法本身正确：`DatabaseHelper.ets:221-249`。
- DDL 未 await：`DatabaseHelper.ets:211-252`、`TripDao.ets:259`；版本号写入 `DatabaseHelper.ets:255`，catch 在 `:258`。
- 事务骨架存在：`DatabaseHelper.ets:167-183`（begin/commit/rollBack）与 `:207` / `:256` / `:259`。
