# Token 鉴权系统收到 401 后必须有自动恢复通道

## Scenario

应用使用 BFF（Backend for Frontend）架构，客户端通过设备激活获取 Bearer token，后续所有请求带在 Authorization 头里。当 token 过期或失效时，BFF 返回 401。如果客户端没有自动恢复机制，用户将陷入"永久 401"状态——每次请求都失败，但没有任何动作去重新获取 token。

典型表现：开发期 Mock 模式下一切正常（不需要 token），接入真实 BFF 后首次激活失败就再也无法恢复，必须重启应用。

## Key Signals

- HTTP 请求收到 401 后仅抛错或记日志，没有调用重新激活流程
- token 为空时请求仍然发出（仅告警），不带 Authorization 头继续请求
- 重试逻辑对所有错误无差别重试——401 重试注定失败，因为 token 仍然无效
- 激活方法的 catch 分支只记日志返回 false，调用方的 catch 分支是空函数体
- 全项目搜索未发现任何地方在收到 401 后调用重新激活

## Essence

问题的根源是：**401 是一个"可恢复"的错误，但系统把它当作"不可恢复"的通用错误处理了**。

401 与 500/502/503 有本质区别：
- 500/502/503：服务端临时不可用，重试可能成功
- 401：token 失效，重试不可能成功，但重新激活后可以成功

缺少自动恢复通道意味着：
1. 用户首次激活失败后，所有后续 BFF 请求都带空 token 或无效 token
2. 没有任何地方监听 401 并触发重新激活
3. 用户必须手动重启应用才能恢复

## Approach

1. **在 HTTP 传输层捕获 401 并触发恢复**：当收到 401 时，先尝试重新激活（调用 `reactivate()`），激活成功后用新 token 重试原请求；激活失败才抛错给调用方。
2. **区分可重试与不可重试错误**：401 在重新激活后可重试；402/429 在退避后可重试；500/502/503 在退避后可重试；其他错误不重试。
3. **token 为空时不发请求**：直接触发激活流程，而非带空 token 发请求后等 401。
4. **激活失败后设置重试计数器**：避免在 token 持续无效时无限重试激活，设置最大重试次数（如3次）后停止。
5. **reactivate 与 activate 的并发控制**：reactivate 先 clear 再 activate，如果 activate 正在进行中，reactivate 不应直接返回 false（这会导致 token 被清除但未重新激活），而应等待当前激活完成或强制重新激活。

```typescript
// ❌ 错误：401 仅抛错，无恢复动作
if (resp.responseCode === 401) {
  throw new AppError(ErrorCode.CLOUD_TOKEN_INVALID, 'token 失效');
}

// ✅ 正确：401 后自动重新激活并重试
if (resp.responseCode === 401) {
  const recovered = await DeviceActivator.reactivate(context);
  if (recovered) {
    // 用新 token 重试原请求
    return this.complete(req, idempotencyKey);
  }
  throw new AppError(ErrorCode.CLOUD_TOKEN_INVALID, 'token 失效且重新激活失败');
}
```

## Faster Next Time

- 在设计 token 鉴权系统时，401 的恢复通道是必须项而非可选项——在架构评审清单中加入"401 后是否有自动恢复"
- 搜索全项目的 401 处理代码，确认每个 401 都有对应的恢复动作
- 检查 token 为空时的行为：是继续发请求（错误）还是先激活（正确）
- 检查重试逻辑是否区分可重试与不可重试错误——401 不重试、500 重试

## Applicability Boundaries

- **适用**：所有使用 Bearer token 鉴权的客户端-服务端架构，包括 BFF、微服务、第三方 API
- **不适用**：使用 session cookie 鉴权的传统 Web 应用（cookie 过期由浏览器处理）；无鉴权的公开 API
- **注意**：重新激活也需要并发控制——多个请求同时收到 401 时，只应触发一次重新激活，其他请求等待结果
- **与降级可观测性的关系**：本经验关注 401 的自动恢复通道，`2026-11-01-null-fallback-needs-observability-and-cancel` 关注降级的可观测性与取消通道，两者互补
