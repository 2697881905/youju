# ArkTS 中 JSON.parse as Type 不做运行时校验的类型安全风险

## Scenario

在 ArkTS（HarmonyOS 的开发语言）中，`JSON.parse()` 返回 `Object` 类型。开发者通常使用 `as Type` 类型断言将其转换为具体的接口类型，然后直接访问字段。但 ArkTS 的 `as` 类型断言**不做运行时校验**——它只是告诉编译器"相信我，这个对象的类型是 X"，实际运行时如果 JSON 结构与预期类型不匹配，字段访问会返回 `undefined` 或抛 `TypeError`。

这种模式在开发期 Mock 数据下不会暴露问题（Mock 数据总是符合预期结构），但在真实网络环境下，BFF 返回的 JSON 可能缺少字段、字段类型不匹配、或返回完全不同的错误结构。

## Key Signals

- `JSON.parse(String(resp.result)) as SomeInterface` 后直接访问 `.field` 不检查 undefined
- 外部 API 返回错误时 JSON 结构与正常响应不同，`as Type` 断言后字段全为 undefined
- 持久化缓存中的 JSON 格式随版本升级发生变化，`as Type` 断言后旧数据字段缺失
- 运行时出现 `Cannot read property 'xxx' of undefined` 错误

## Essence

ArkTS 的 `as` 类型断言是**编译时类型标注**，不是**运行时类型校验**。这与 TypeScript 的 `as` 行为一致——它不会在运行时检查对象是否真的符合目标类型。

关键区别：
- **类型守卫（Type Guard）**：运行时逐字段校验，确认对象符合类型后才使用——安全但代码量大
- **类型断言（`as Type`）**：编译时告诉编译器类型，运行时不校验——简洁但不安全
- **Schema 校验**：用 JSON Schema 或类似机制在 parse 后做完整结构校验——最安全但最重

`JSON.parse as Type` 模式的风险在于：parse 成功（JSON 合法）≠ 结构符合预期类型。JSON 可以是合法的 `{}`，但断言为 `ActivateResponse` 后访问 `.deviceToken` 会得到 `undefined`。

## Approach

1. **关键路径使用类型守卫**：对 BFF 响应、IAP 校验响应等关键数据，parse 后用类型守卫逐字段校验：

```typescript
// ❌ 风险：直接断言后访问字段
const data: ActivateResponse = JSON.parse(String(resp.result)) as ActivateResponse;
const token: string = data.deviceToken; // 如果字段缺失，得到 undefined

// ✅ 安全：parse 后逐字段校验
const raw: Object = JSON.parse(String(resp.result));
if (typeof raw !== 'object' || raw === null) {
  throw new AppError(ErrorCode.JSON_PARSE_FAILED, '响应不是对象');
}
const obj: Record<string, Object> = raw as Record<string, Object>;
const deviceToken: Object | undefined = obj['deviceToken'];
if (typeof deviceToken !== 'string' || deviceToken.length === 0) {
  throw new AppError(ErrorCode.SCHEMA_VALIDATION_FAILED, 'deviceToken 缺失或非字符串');
}
```

2. **非关键路径至少包 try/catch**：所有 `JSON.parse as Type` 必须在 try/catch 内，确保 TypeError 不会导致崩溃。虽然这不能防止数据错误，但能防止应用崩溃。

3. **持久化数据加版本标记**：缓存的 JSON 中加入版本字段，读取时先检查版本，版本不匹配时丢弃缓存而非断言后使用。

4. **对 undefined 字段做保守默认**：parse 后对可能缺失的字段给保守默认值，而非直接使用：

```typescript
const data: VerifyResponse = JSON.parse(String(resp.result)) as VerifyResponse;
const verified: boolean = data.verified ?? false; // 缺失时默认 false
```

## Faster Next Time

- 代码审查时搜索 `JSON.parse.*as` 模式，确认每个都在 try/catch 内
- 对 BFF 响应解析，优先使用已有的类型守卫工具（如 `TripParser` 的三层防线模式）
- 对持久化缓存数据，加版本标记并在读取时校验版本
- ArkTS 严格模式下 `as` 断言不做运行时校验——这是语言规范行为，不是实现细节

## Applicability Boundaries

- **适用**：所有 ArkTS/TypeScript 项目中使用 `JSON.parse as Type` 模式的代码
- **不适用**：使用 Zod、io-ts 等运行时类型校验库的项目（这些库在 parse 时自动校验）
- **注意**：ArkTS 严格模式禁止 `any` 类型，但不禁止 `as Type` 断言——`as` 是合法但需要谨慎使用的特性
- **与 Schema 校验的关系**：如果项目已有 JSON Schema 校验机制（如 LLM 响应的三层防线），`as Type` 在 Schema 校验通过后使用是安全的；风险在于跳过 Schema 校验直接断言

## Evidence or Examples

在 HarmonyProject2 项目中发现的 `JSON.parse as Type` 使用情况：

- `DeviceActivator.ets:72`：`JSON.parse(String(resp.result)) as ActivateResponse` — parse 后直接访问 `.deviceToken.length`，字段缺失时抛 TypeError（被外层 catch 捕获）
- `IapStore.ets:205`：`JSON.parse(String(resp.result)) as VerifyResponse` — parse 后直接访问 `.verified`，字段缺失时得到 undefined
- `EntitlementStore.ets:58`：`JSON.parse(rawJson) as Entitlement` — 持久化缓存数据，格式随版本变化时字段可能缺失
- `LlmClient.ets:314`：`JSON.parse(String(resp.result)) as ChatCompletion` — LLM 响应解析，已有后续的类型守卫检查（相对安全）
- 全项目共18处 `JSON.parse as Type` 模式，均在 try/catch 内，不会导致崩溃，但类型不匹配时错误信息不够明确
