# 端侧 LLM 应用 BFF 最小实现结构——Express 三层 + SQLite + JWT + 幂等 + 配额三态

## Scenario
端侧 LLM 应用需要从"直连 LLM 供应商"转向"经 BFF 中转"，以解决 Key 安全、用量控制、计费和防刷四个问题。BFF 的最小实现需要覆盖：设备激活、权益查询、行程生成（含配额扣减和 LLM 代理）、IAP 校验、IAP webhook。过度设计会拖长开发周期，设计不足会导致并发扣费、重复扣费或审计缺失。

## Key Signals
- 如果用余额字段（`balance INT`）做配额扣减，并发请求会互相覆盖，且无法审计历史变动——一次退款回收需要回溯所有扣减记录才能算出正确余额。
- 如果幂等只在接口入口检查（"这个 key 来过了"），而不贯穿到配额扣减（"这个 key 的扣减是否已结算"），网络重试仍然会导致重复扣费。
- 如果 BFF 设计成微服务架构（独立账号服务、计费服务、LLM 代理服务），开发周期会从 2 天变成 2 周，而当前用户量为零时不需要这种复杂度。

## Essence
BFF 的最小实现是"Express 三层目录 + SQLite + JWT + 幂等中间件 + 配额三态"，不是一整套微服务。核心设计决策有三个：① 配额用 ledger（追加日志）而非余额字段，② 幂等贯穿到配额扣减（同一 key 的 reserved → committed/released 只发生一次），③ 扣减顺序按"对用户最有利"排（订阅日额度 → 通行证 → 赠送次数）。

## Approach
1. **目录结构**（三层）：
   ```
   bff/src/
     routes/        — 5 个路由文件（device/entitlement/trip/iap）
     middleware/    — auth（JWT 票据验证）+ idempotency（幂等检查）
     services/      — quota（配额三态）+ llm（DeepSeek 代理）+ iap（IAP 校验）
     db.js          — SQLite 初始化 + 6 张表 DDL
     index.js       — Express 入口
   ```
2. **6 张表**：`account`、`subscription`、`trip_pass`、`quota_ledger`、`trip_request`、`order`。不存 `balance` 字段——余额用 `quota_ledger` 聚合计算。
3. **JWT 票据**：`/v1/device/activate` 返回 JWT（含 accountId/deviceId），后续请求带 `Authorization: Bearer <token>`。`auth.js` 中间件验证 JWT 并注入 `req.accountId`。
4. **幂等中间件**：`idempotency.js` 检查 `Idempotency-Key` 头，在 `trip_request` 表中查状态——`pending`（正在处理，返回 409）、`succeeded`（返回缓存结果）、`failed`（允许重试）、不存在（新建 pending 记录）。
5. **配额三态**（`quota_ledger` 表）：
   - `reserved`：预扣，请求开始时写入。
   - `committed`：结算，LLM 返回成功后写入。扣 1。
   - `released`：回滚，LLM 超时/5xx 后写入。不扣。
   - 同一 `idempotency_key` 的 reserved → committed/released 只发生一次。
6. **扣减顺序**：订阅日额度 → 通行证 → 赠送次数。订阅有效期内不会碰通行证，通行证有效期内不会碰赠送次数。
7. **LLM 代理**：`llm.js` 接收端侧的 OpenAI 兼容格式请求，注入 `API_KEY`，转发到 DeepSeek，返回 `content` + `usage`。端侧不需要知道 Key 和供应商。

## Faster Next Time
- 不要用余额字段做配额——用 ledger（追加日志）聚合计算余额，并发安全且可审计。
- 幂等不是接口层的独立检查，而是贯穿到配额扣减的完整链路——`idempotency_key` 从 HTTP 头传到 `quota_ledger` 的每一条记录。
- BFF 的最小实现是 5 个接口 + 6 张表 + 3 个中间件，不是微服务——用户量为零时不要过度设计。
- 扣减顺序按"对用户最有利"排，而不是按"对平台最有利"排——先用已付费的权益（订阅），再用品类权益（通行证），最后用赠送。
- `trip_request` 表同时承担幂等记录和用量审计两个职责——不要为审计单独建表。

## Applicability Boundaries
- 适用：端侧 LLM 应用需要 BFF 中转，用户量在 0-10 万级别，接口数 < 10。
- 不适用：用户量 > 10 万或接口数 > 20 的场景——此时需要考虑读写分离、缓存层、消息队列等扩展。
- SQLite 在单机并发写入下有 `busy` 风险——如果 QPS > 100，需要迁移到 PostgreSQL 或 MySQL。
- JWT 票据的有效期设计需要在安全性和用户体验之间权衡——太短会导致频繁重新激活，太长会导致票据泄露后无法及时失效。
- IAP 服务端校验的具体实现依赖华为 IAP 校验 API，当前为占位——上线前必须接入真实校验。
- 本经验聚焦 BFF 的实现结构（目录、表、中间件、配额三态），`2026-11-01-end-side-llm-monetization-bff` 聚焦架构决策（为什么做 BFF、控制面/数据面分离）——两者互补，前者是"怎么做"，后者是"为什么做"。

## Evidence or Examples
- BFF 项目结构：`bff/src/routes/{device,entitlement,trip,iap}.js` + `bff/src/middleware/{auth,idempotency}.js` + `bff/src/services/{quota,llm,iap}.js`。
- `quota_ledger` 表结构：`id, account_id, delta, source, ref_type, ref_id, state, idempotency_key UNIQUE, created_at, settled_at`。
- 扣减顺序实现：`services/quota.js` 的 `chargeQuota()` 函数按 subscription → pass → gift 顺序尝试扣减。
- LLM 代理：`services/llm.js` 的 `proxyChat()` 注入 `Authorization: Bearer ${process.env.LLM_API_KEY}`，转发到 `${process.env.LLM_BASE_URL}/chat/completions`。
- 端侧改动：`ApiConfig.ets` 删 `API_KEY`/`BASE_URL`，改 `BFF_BASE_URL` + `LLM_CHAT_ENDPOINT: '/v1/trip/generate'`。
