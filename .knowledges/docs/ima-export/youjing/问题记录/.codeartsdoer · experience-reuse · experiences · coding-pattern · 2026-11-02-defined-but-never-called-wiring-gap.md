# "定义但不调用"——代码接线缺口的最常见模式

## Scenario

项目完成大规模改造（如商业化、架构迁移、安全加固）后，新增了大量方法、错误码、判定逻辑。代码审查时这些内容"看起来都有"，但实际上从未被任何调用方使用——功能形同虚设。这类缺口在常规审查中极难发现，因为审查者看到方法定义就认为"已实现"，不会主动去验证"是否有人调用了它"。

## Key Signals

以下信号提示可能存在"定义但不调用"的接线缺口：

1. 方法名只在定义文件中出现，grep 全工程命中数 ≤ 1
2. 错误码常量只在定义表中出现，无任何 throw 或 catch 引用
3. 恢复/重试/降级方法已实现（如 `reactivate()`），但错误处理流程中直接走到失败页面而非调用恢复方法
4. 判定方法（如 `canGenerate()`、`canExport()`）返回 boolean，但调用方从未检查返回值或根本未调用

## Essence

"定义但不调用"是接线缺口的最常见形态。它的危险性在于**代码审查无法发现**——审查者看到定义就标记"已完成"，不会主动验证调用链。只有通过 grep 搜索方法名/错误码，统计命中数，才能确认是否真正接线。

与"死代码"不同：死代码是曾经调用过但后来移除了调用方；"定义但不调用"是从未接线，通常发生在新增模块时——开发者先写了基础设施（方法、错误码、判定逻辑），计划后续接线，但接线步骤被遗漏。

## Approach

### 检测步骤

1. **提取所有新增方法名和错误码常量名**
2. **对每个名称做 grep 搜索**，统计命中文件数和命中行数
3. **命中数 ≤ 1（仅定义处）→ 标记为"未接线"**
4. **命中数 = 2（定义处 + 1 个调用方）→ 验证调用方是否在正确位置调用**
5. **命中数 ≥ 3 → 大概率已接线，但仍需验证调用上下文是否正确**

### 分类处理

| 缺口类型 | 典型表现 | 严重程度 |
|----------|----------|----------|
| **判定方法未调用** | `canGenerate()` 定义了但生成前无人检查 | 严重——付费墙/额度检查被绕过 |
| **恢复方法未调用** | `reactivate()` 定义了但 401 后无人触发 | 阻断——故障不可自愈 |
| **错误码无 catch** | `CLOUD_RATE_LIMITED` 定义了但无 catch 处理 | 一般——错误体验降级 |
| **错误码无 throw** | `CLOUD_IAP_VERIFY_FAILED` 定义了但无人抛出 | 一般——错误场景未覆盖 |

## Faster Next Time

- **改造完成后立即做 grep 扫描**：不要等"感觉有问题"再查，新增模块后立即 grep 所有新方法名
- **用 `grep -c` 统计命中数而非逐条阅读**：命中数 ≤ 1 就是红旗，不需要读代码内容就能判断
- **检查 import 但未调用的方法**：有些文件 import 了类但从未调用其方法，grep import 语句可以快速发现
- **在 PR 模板中加入"接线验证"检查项**：新增方法/错误码时，要求 PR 描述中列出调用方位置

## Applicability Boundaries

- **适用**：大规模改造后（商业化、架构迁移、安全加固）的接线验证；新增模块后的回归检查；代码审查中的"接线完整性"维度
- **不适用**：纯重构（方法名变了但调用方也同步更新）；从零开始的新项目（还没有足够的方法定义）；删除功能后的清理验证（这是"调用但不定义"的反向问题）
- **前提**：项目有明确的接口设计文档或方法清单，否则不知道该 grep 哪些名称

## Evidence or Examples

在 HarmonyProject2 商业化改造中发现 4 个"定义但不调用"缺口：

1. **`EntitlementStore.canGenerate()`**（`EntitlementStore.ets:93`）——额度预检判定方法，定义了 `giftRemaining > 0` 逻辑，但 grep 全工程仅 1 处命中（定义处），`GeneratingPage` 发起生成前从未调用——免费用户 3 次赠送额度在端侧无体现

2. **`DeviceActivator.reactivate()`**（`DeviceActivator.ets:100`）——票据失效后重新激活方法，实现了"清旧 token + 重新 activate"逻辑，但 grep 全工程无调用方——`LlmClient.ets:301` 抛出 `CLOUD_TOKEN_INVALID` 后直接进入失败页面，而非调用 reactivate 自动恢复

3. **`CLOUD_RATE_LIMITED` (6003)**（`ErrorCode.ets:44`）——频率超限错误码，`LlmClient.ets:307` 会抛出，但 grep 全工程无任何 catch 处理此错误码——用户看到的是通用失败提示而非"频率超限，请稍后重试"

4. **`CLOUD_IAP_VERIFY_FAILED` (6006)**（`ErrorCode.ets:47`）——IAP 校验失败错误码，定义了但全工程无任何 throw 或 catch——`IapStore` 在 BFF 校验未通过时只返回 `{ success: false }` 而非抛出此错误码
