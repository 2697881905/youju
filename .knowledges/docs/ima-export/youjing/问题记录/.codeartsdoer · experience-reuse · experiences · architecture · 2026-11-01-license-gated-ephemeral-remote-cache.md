# 外部数据源回退只在本地种子为空时启用，许可未定前结果只进内存 TTL 缓存不落库

## Scenario
应用有内置种子数据可离线使用，又接入第三方地点/内容/天气 API 补充未覆盖的城市。需要决定三件事：什么时候调用外部、结果要不要持久化、缓存多久。

## Key Signals
- 外部 API 的许可/条款尚未确认，代码却已经把结果写进本地数据库或磁盘缓存。
- 种子数据与远端数据写同一张表，行上无法区分来源，展示时也无法判断可信度与时效。
- 未支持的城市请求返回空，界面用默认城市数据填充（数据冒充）。
- 每次冷启动都重新请求同一城市，说明缓存只在前台会话内有效或根本不存在。

## Essence
数据源路由的核心不是"多级 fallback"本身，而是每一级的**写入权限**与**可信边界**。种子数据可持久化、可离线、行为确定；外部数据在许可未定时只能作为会话内补充——落库会把"临时可用"变成"永久分发"，同时让来源和时效不可追溯。路由顺序应是"确定性与已授权数据优先，外部只补空缺"，并且空缺要用空态表达，不能拿别的城市数据冒充。

## Approach
1. 定义明确的三级路由：演示/测试 mock（仅限特定城市）→ 本地种子库 → 外部 API（仅当种子为空且城市在允许范围）。
2. 外部结果只放进程内缓存并设 TTL（如 30 分钟），不写 RDB、不写磁盘文件；进程重启即失效。
3. 外部缺失字段给保守默认（评分按检索秩、预约能力一律 false），并在 UI 标注"以官方为准"，不伪造。
4. 种子与外部各自独立回退；种子有数据时永不联网，保证内置城市行为稳定、可复现。
5. 无数据时返回空列表，由调用方渲染空态，不用其他城市数据兜底。
6. 在文件头写明许可边界，以及"许可确认后可以升级为持久缓存"的触发条件与需要补的字段（来源、版本、过期时间）。
7. 验收三件事：断网冷启动断言内置城市完全可用；杀掉进程再启动，断言外部城市不再命中（证明确实没落盘）；grep 外部结果对象的所有写入点，确认只有进程内 Map、没有 RDB/Preferences/文件写。

## Faster Next Time
- 评审"加缓存"提案先问三句：这份数据的许可允许存储吗？允许存多久？允许再分发吗？
- 看到外部结果写库，先查来源字段（provenance/source）能否区分本地种子与远端数据。
- 判断回退顺序的口诀：确定性 > 可离线 > 已授权 > 外部现取。
- 把"不支持的城市返回空"写成显式规则，避免下一个人以"体验不好"为由加默认城市兜底。
- 判断"是否真的没落库"不要只看注释和变量名：进程重启后命中归零、grep 不到 RDB/Preferences 写入点，才算证据。

## Applicability Boundaries
- 适用：第三方地图/内容/天气 API 的补充数据，许可未定或仅按会话授权；本地优先、弱网可用的应用。
- 不适用：已签署持久化许可、需要离线可用的数据（应落库并带版本/来源/过期时间）；或要求强一致的业务数据。
- 许可确认或条款变更后应重新评估缓存层级，而不是沿用"只放内存"。
- 与读侧派生经验的共同点：两者都拒绝为「可重建的结果」或「未授权的临时数据」建立第二份持久真相，区别只是落点——派生在计算侧（见 `2026-11-01-derive-view-over-new-table`），外部数据在写入侧。

## Evidence or Examples
- 三级路由与"种子为空才联网"：`entry/src/main/ets/data/PlanRepository.ets:19-37`（mock 仅京都 `:22-25`；种子库 `:26`；`spots.length === 0 && isMapCity` 才回退 `:27-32`；不支持城市返回空 `:33-36`）。
- 内存 30 分钟 TTL、明确不落库：`data/MapKitCityStore.ets:6`、`:27`、`:39-46`。
- 外部字段不可得时的保守映射（按检索秩给热度、预约一律 false）：`data/MapKitCityStore.ets:4-7`。
- 种子幂等与版本触发 upsert：`data/DataSeeder.ets:9-10`、`:30-31`。
