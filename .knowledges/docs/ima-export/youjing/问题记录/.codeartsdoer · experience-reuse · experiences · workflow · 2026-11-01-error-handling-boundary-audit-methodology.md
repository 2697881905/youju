# 错误处理与边界条件系统性普查方法论

## Scenario

当应用接入外部服务（BFF、IAP、LLM API）后，错误处理散落在各模块中，每个模块的 catch 分支各自为政。功能测试通常验证"正常路径能走通"，但很少覆盖"失败后能否恢复"、"空值时是否崩溃"、"并发时是否竞争"这类边界场景。这类问题在开发期 Mock 模式下完全不可见，只有在真实网络环境和真实用户行为下才暴露。

触发条件：应用有3个以上外部依赖（网络请求、IAP、第三方 API），且有本地缓存/状态与远端数据的一致性需求。

## Key Signals

以下信号提示需要做一次错误处理与边界条件普查：

1. 外部服务返回错误码后，应用没有任何自动恢复动作（如重新激活、重新登录）
2. 数据加载方法返回 null 时，部分调用方没有 UI 兜底（空白页面、无错误提示）
3. 并发防护标志（如 `purchasing`、`activating`）只覆盖部分入口（如 `restorePurchases` 不检查 `purchasing`）
4. 缓存 TTL 存在但判定函数不检查缓存是否过期（直接读 cached 字段）
5. 付费流程中 BFF 校验失败后不确认发货（`finishPurchase` 未调用），用户已付款但无权益

## Essence

错误处理普查的核心是：**按"失败链路"而非"功能模块"组织检查维度**。关键在于把检查维度固定为5类，每类都有明确的验证方法和证据要求：

1. **网络请求错误处理**：每个 HTTP 错误码是否有对应的恢复动作？失败后主流程是否被阻断？
2. **空值与边界条件**：数据加载方法返回 null 时各调用方是否一致处理？未初始化时调用方法会怎样？
3. **并发与状态竞争**：防护标志是否覆盖所有入口？缓存 TTL 与实时数据之间是否有一致性风险？
4. **语言/平台严格模式兼容性**：类型断言是否做运行时校验？是否有不符合严格模式的写法？
5. **UI 层异常处理**：aboutToAppear 中异步操作失败时 UI 是否有兜底？购买/导出过程中状态是否正确管理？

## Approach

### 准备阶段

1. 列出所有外部依赖（BFF、IAP、LLM、地图服务等）及其错误码
2. 列出所有返回 null/空值的数据加载方法及其调用方
3. 列出所有并发防护标志及其保护范围
4. 列出所有缓存机制及其 TTL 配置

### 逐维度检查

**维度1：网络请求错误处理**
- 对每个 HTTP 请求，检查 401/402/429 等错误码是否有对应的恢复动作（如重新激活、降级提示）
- 检查错误是否区分"可重试"与"不可重试"——401 重试注定失败，不应浪费资源
- 检查付费流程中 BFF 校验失败后是否仍确认发货（避免用户付款后无权益）

**维度2：空值与边界条件**
- 对每个返回 null 的数据加载方法，逐个检查调用方是否有 null 处理
- 检查未初始化时调用方法的行为（返回默认值？抛错？静默失败？）
- 检查 null 处理是否一致——有些调用方正确降级，有些仅记日志无 UI 反馈

**维度3：并发与状态竞争**
- 检查每个并发防护标志是否覆盖所有入口方法（如 `restorePurchases` 是否也检查 `purchasing`）
- 检查缓存 TTL 是否被判定函数实际使用（存在 `isCacheValid()` 但 `canExport()` 不调用它）
- 检查"先 clear 再 activate"类操作与并发调用之间的竞争窗口

**维度4：语言/平台严格模式兼容性**
- 搜索 `JSON.parse(...) as Type` 模式，检查是否在 try/catch 内
- 搜索 `= undefined` 赋值，检查是否有对应的 `| undefined` 类型声明
- 搜索 `any` 类型使用，确认是否违反严格模式

**维度5：UI 层异常处理**
- 对每个页面的 aboutToAppear，检查异步操作失败时是否有 UI 状态变更（而非仅日志）
- 检查购买/导出等操作的状态变量是否有 try-finally 保护
- 检查数据未加载完成时用户点击操作按钮的行为（toast 提示？静默无响应？）

### 证据要求

每个发现的问题必须给出 `file:line` 证据，并标注严重程度：
- **阻断**：用户无法完成主流程
- **严重**：用户会遇到可见的错误行为或数据丢失
- **一般**：边界场景或降级体验不佳，不影响正常使用

## Faster Next Time

- 把5个维度做成检查清单，每次新增外部依赖或数据加载方法时逐项过一遍
- 对每个 HTTP 请求，在编码时就问："401 后怎么办？重试有意义吗？"
- 对每个返回 null 的方法，在编码时就问："所有调用方都处理 null 了吗？UI 有反馈吗？"
- 对每个并发防护标志，在编码时就问："所有入口都检查了吗？"
- 评审时把"BFF 校验失败后是否确认发货"当作付费流程的硬性检查项

## Applicability Boundaries

- **适用**：有3个以上外部依赖的应用、有付费流程的应用、有本地缓存与远端数据一致性需求的应用
- **不适用**：纯本地应用（无网络请求）、单页面应用、无并发场景的简单应用
- **注意**：本方法论关注的是"错误处理与边界条件"而非"功能正确性"，功能测试不在普查范围内
- **与主链路完整性普查的关系**：本方法论是 `2026-11-01-main-flow-integrity-audit` 的互补维度——前者关注链路完整性，本方法论关注错误处理与边界条件

## Evidence or Examples

在 HarmonyProject2（有径/YouJing）项目中执行的一次完整普查：

- 普查覆盖5个维度，发现15个问题：0阻断、3严重、12一般
- 3个严重问题：
  - HttpLlmTransport 401 错误未触发重新激活，重试注定失败（LlmClient.ets:300-301, 380-398）
  - DeviceActivator 激活失败后无自动恢复机制，后续 BFF 请求永久 401（DeviceActivator.ets:88-90, Index.ets:103-104）
  - IapStore verifyWithBff 失败后未 finishPurchase，用户已付款但无权益（IapStore.ets:62-64, 200-202）
- 12个一般问题涵盖：null 处理不一致、缓存 TTL 未检查、并发标志覆盖不全、JSON.parse 无运行时校验、UI 层无兜底提示等
