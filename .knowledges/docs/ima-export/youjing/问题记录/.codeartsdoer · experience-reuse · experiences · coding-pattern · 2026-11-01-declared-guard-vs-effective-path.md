# 读到防护分支不等于防护生效：审计要追踪开关常量到实际请求体

## Scenario
系统对外宣称有"三层防线"保护模型输出：提示词内嵌 JSON Schema、请求参数 `response_format` 严格模式、端侧逐字段守卫。代码审查时第三层写得最完整，第二层的 `json_schema/strict` 分支也写得像模像样，很容易得出"三层齐备"的结论——但真正决定它是否执行的开关常量在生产配置里是 `false`。

## Key Signals
- 某个防护由配置常量控制，而该常量的默认值是 `false`、空串或空数组。
- 分支代码存在，但搜索调用点找不到任何把它置为 `true` 的路径。
- 实际发出的请求体里缺少宣称的字段（例如只有 `{"type":"json_object"}`）。
- 全局开关名义上控制某功能，实际只在一条调用链里被读取，其他同类调用链根本不判断它。
- Schema 文本在提示词里内嵌一份、在守卫里再写一份枚举白名单，二者靠人工同步。

## Essence
防护强度等于 `min(代码分支, 运行时配置)`。开关为假时，那个分支是**死代码**，把它计入防线就是高估。审计的唯一可靠依据是"实际发出的请求体 + 实际执行到的路径"，而不是"源码里有没有这个 if"。

## Approach
1. 对每一条宣称的防护，找出决定它是否执行的那个变量（config / feature flag / build 变量），确认它的**默认值**和**生产值**，不要只看分支条件。
2. 用日志或抓包核对实际请求体字段集合，与宣称做逐项对照。
3. 若开关不满足，显式把该层降级记录进设计（例如"第二层退化为 json_object，只保证是合法 JSON，不保证结构"），并据此调整对后续层的预期——不要一边降级一边继续宣称严格模式。
4. 让 schema、枚举白名单、守卫共用同一常量源，避免"提示词改了、守卫没改"。
5. 对全局开关核对**覆盖范围**：列出所有同类调用点，确认每个都读取了新开关；只覆盖一条链路的开关要在命名或注释上写清适用范围。
6. 在 CI 或单测里加一条断言：当"支持严格模式"为真时，构造出的请求体必须包含 `json_schema`；为假时不得出现该字段，防止配置与请求体再次脱节。

## Faster Next Time
- 评审口诀：每个"防线/校验/开关"都要回答三问——**代码在哪、开关在哪、当前值是什么**。任一答不上就按"不存在"处理。
- 一条 grep 定位：搜 `SUPPORTS_`、`ENABLE_`、`USE_`、`STRICT` 类常量名，逐个看默认值。
- 见到"分支写了但没人置真"时，优先怀疑它是历史遗留，而不是以为运行时被打开。

## Applicability Boundaries
- 适用：有多层校验、灰度开关、mock/real 双路径、构建期裁剪的客户端或服务端代码；对外承诺"我们有 N 层防护"的任何场景。
- 不适用：开关只影响展示效果、不涉及正确性或安全性的场景，此时只需一句注释说明默认值。

## Evidence or Examples
- 第一层存在且真实生效：`entry/src/main/ets/ai/PromptBuilder.ets:64-65` 内嵌 `TripSchema.TRIP_JSON_SCHEMA`；常量在 `entry/src/main/ets/ai/TripSchema.ets:23`。
- 第二层名存实亡：`entry/src/main/ets/common/config/ApiConfig.ets:87` 的 `SUPPORTS_JSON_SCHEMA: false`，使 `entry/src/main/ets/ai/LlmClient.ets:260-273` 的 strict 分支永不进入，实际只下发 `json_object`。
- 开关覆盖不全：`entry/src/main/ets/common/config/MockConfig.ets:14` 的 `USE_MOCK_DATA` 只在 `entry/src/main/ets/ai/LlmClient.ets:357-358` 选择传输实现，重排（`ReplanClient`）与天气（`WeatherClient`）不读取该开关。
- 同源反例：`TripSchema` 同时被提示词与 `TripParser` 引用，说明"同源"这件事能做对，第二层的开关没做到。
