# 类型守卫原语要单一实现，并补上语义级校验（NaN、Infinity、非法时刻）

## Scenario
系统要从三处不可信输入构建领域对象：模型返回的行程 JSON、云函数返回的重排决策、第三方天气 API。每处都配了一份"逐字段类型守卫"，函数名和实现几乎相同（`asObj` / `asArr` / `reqStr` / `reqNum` / `reqInt` / `reqTime`），字段级调用也写得很密。看起来校验完备，实际存在能穿透的类型与取值漏洞。

## Key Signals
- 三个不同模块里出现结构近乎逐行相同的 `asObj` / `asArr` / `reqXxx` 实现。
- 守卫只做 `typeof v === 'number'`，随后该值直接参与加减、比较、格式化。
- `JSON.parse('{"a":1e999}')` 得到 `Infinity`，但仍被判定为合法 number。
- 整数校验只查"是整数"，不查上下界；时间校验只匹配 `\d{2}:\d{2}`，于是 `99:99` 通过。
- 下游出现 `NaN`、`Invalid Date`、`24:70` 之类的展示，且报错路径难以定位到底是哪一段 JSON 坏了。

## Essence
`typeof x === 'number'` 不是数值有效性检查：`NaN` 与 `±Infinity` 都属于 number。格式正则也不蕴含语义有效（小时 00-23、分钟 00-59、日期必须真实存在）。守卫的职责是"这个值能安全参与后续算术与渲染"，因此需要**类型 → 有限性 → 区间 → 语义**四层，缺一层就会把错误推迟到更难排查的地方。同时，守卫原语被复制成三份后必然各自漂移——修复只落在其中一份，漏洞留在另外两份。

## Approach
1. 抽出单一守卫模块，导出带字段路径参数的原子函数，例如 `asObj(v, path)`、`asArr(v, path)`、`reqStr`、`optStr`、`reqNum`、`reqInt`、`reqEnum`、`reqTime`、`reqIsoDate`；错误统一抛带 `$...` 路径的领域异常。
2. `reqNum`：先用 `typeof v === 'number'`，再补 `Number.isFinite(v)`。
3. `reqInt`：在 finite 基础上补 `Number.isInteger(v)` 与 `[min, max]` 区间参数，不要调用方各自再判一次。
4. `reqTime`：正则通过后继续解析出时/分并校验 `h <= 23 && m <= 59`；跨字段约束（如 `endTime > time`）单独一层。
5. `reqIsoDate`：校验日期真实存在（拒绝 `2026-02-31`），而不是只匹配 `\d{4}-\d{2}-\d{2}`。
6. 枚举白名单只存在于 schema 常量文件，解析器引用而不复制；改枚举只需改一处。
7. 为每个原语写一张边界用例表并纳入单测：`NaN`、`Infinity`、`-Infinity`、字符串数字 `"12"`、超范围整数、`"99:99"`、`"2026-02-31"`、空数组、`null`、缺字段。
8. 解析入口先剥壳（去代码围栏、取首个 `{` 到末个 `}`），再交给守卫；剥壳失败与字段失败使用不同错误码，便于区分"模型没输出 JSON"和"模型输出了错的 JSON"。

## Faster Next Time
- 三条 grep 就能查出这类漏洞：`typeof .*=== 'number'`、`\\d{2}:\\d{2}`、注释里的"只做结构校验"。
- 评审时先问"这个数值后面会不会参与算术或格式化"；会，就必须有有限性与区间校验。
- 发现第二份 `asObj` 就先合并，再看逻辑——重复的守卫比错误的守卫更危险，因为它让人以为已经覆盖。

## Applicability Boundaries
- 适用：解析不可信外部输入的任意语言客户端/服务端，尤其是 LLM 结构化输出、第三方 API、云函数响应。
- 不适用：进程内受信对象之间的传参、已经过上游强校验且同一事务内传递的数据——重复校验只会增加噪声。
- 注意：不同语言的"数值有效"语义不同（JS 的 `Number.isFinite`、Java 的 `Double.isFinite`、Python 的 `math.isfinite`），移植时别照抄判定条件。

## Evidence or Examples
- 守卫原语三处重复实现：`entry/src/main/ets/ai/TripParser.ets:179-298`、`entry/src/main/ets/ai/ReplanParser.ets:94-151`、`entry/src/main/ets/common/weather/WeatherParser.ets:98-138`。
- 数值漏洞：`TripParser.ets:258-266` 的 `reqNum` 不拒绝 `NaN` / `Infinity`；`TripParser.ets:268-274` 的 `reqInt` 不校验范围。
- 时间漏洞：`TripParser.ets:285-291` 的 `reqTime` 只验格式，`"99:99"` 可以通过；跨字段约束 `endTime > time` 另在 `TripParser.ets:148-151` 处理，说明"格式"和"语义"确实被拆成了两层，只是第一层漏了取值域。
- 同源做得对的部分：枚举白名单集中在 `entry/src/main/ets/ai/TripSchema.ets:16-21`，三处解析器都引用它——可作为"原语也该这样收口"的现成先例。
