# ForEach 的 key 必须是稳定标识，混入易变状态会导致全量重建

## Scenario

ArkUI 的 `ForEach` 组件用于列表渲染，其 `keyGenerator` 参数决定列表项的唯一标识。当 key 包含随用户交互变化的字段（如当前选中项 ID、输入框内容）时，每次交互都会导致 key 变化，进而触发该列表组的全量重建——即使列表数据本身没有变化。

## Key Signals

1. `ItineraryPage.ets:1342` 的 `ForEach` key 混入 `focusActId`（当前聚焦的活动 ID），用户点选一个活动时，整个活动列表的 key 全部变化，触发全量重建。
2. `ExpensePage.ets:503` 的 `ForEach` key 混入 `inputCategory`（当前输入的分类），用户切换分类时账单列表全量重建。
3. 全仓 0 处 `LazyForEach`，长行程（多天 × 多活动）和长账单全量渲染，仅靠 `cachedCount(6)` 缓解（`ItineraryPage.ets:1349`、`OnTripPage.ets:1317`、`ExpensePage.ets:945`）。
4. 交互反馈仅靠 1.6s `setTimeout` 清高亮（`ItineraryPage.ets:163-167`），全仓 0 处动画（无 `animateTo/transition`）。

## Essence

ArkUI `ForEach` 的 `keyGenerator` 决定 Diff 算法的项标识。key 的设计原则是：

1. **稳定性**：key 在列表项的生命周期内不应变化。如果 key 随交互状态变化，Diff 算法会认为旧项消失、新项出现，触发销毁+创建的全量重建。
2. **唯一性**：同一列表内不同项的 key 不能重复，否则 Diff 结果不确定。
3. **数据驱动**：key 应来源于列表项本身的不可变标识（如数据库主键、UUID），而非外部交互状态（如当前选中项、输入框值）。

`focusActId` 和 `inputCategory` 是**交互状态**而非**数据标识**——它们的变化频率远高于列表数据本身，混入 key 后使 Diff 算法失效。

## Approach

1. **key 只用数据项的稳定标识**：
   ```typescript
   // 错误：key 含易变状态
   ForEach(activities, (act: Activity) => { ... },
     (act: Activity) => `${act.id}_${this.focusActId}`)
   
   // 正确：key 只用稳定标识
   ForEach(activities, (act: Activity) => { ... },
     (act: Activity) => act.id)
   ```

2. **选中态用条件渲染而非 key 区分**：
   ```typescript
   // 错误：用 key 变化来触发选中样式重建
   // 正确：在项内部用 @State 或 @Prop 驱动样式变化
   .backgroundColor(this.focusActId === act.id ? ColorTokens.primary : ColorTokens.canvas)
   ```

3. **长列表改用 `LazyForEach`**：`LazyForEach` 只渲染可视区域 + 缓存窗口的项，大幅减少渲染量。需要提供 `IDataSource` 实现。

4. **`cachedCount` 不是性能解药**：`cachedCount(6)` 只控制预渲染数量，不改变 ForEach 的全量 Diff 行为。列表项超过 20 条时，ForEach 的 Diff 开销就开始明显。

## Faster Next Time

- Code review 时检查 `ForEach` 的 `keyGenerator`：如果 key 表达式中出现 `this.` 引用的 `@State` 变量，几乎一定是 bug。
- 长列表（>20 项）直接用 `LazyForEach`，不要先用 `ForEach` 再"优化"。
- 选中态、高亮态等交互视觉效果，用条件样式属性（`.backgroundColor()`、`.opacity()`）驱动，不要通过 key 变化触发重建。

## Applicability Boundaries

- **适用**：所有使用 ArkUI `ForEach` 的场景，尤其是列表项需要交互选中、高亮、展开/收起的场景。
- **不适用**：列表项本身确实会增删的场景（key 变化是合理的）；`LazyForEach` 的 `IDataSource` 实现中 key 由数据源管理，不受此约束。

## Evidence or Examples

- `ItineraryPage.ets:1342` — ForEach key 含 `focusActId`，点选活动触发全量重建
- `ExpensePage.ets:503` — ForEach key 含 `inputCategory`，切换分类触发全量重建
- `ItineraryPage.ets:1349` — `cachedCount(6)` 缓解渲染量但不解决 Diff 问题
- 全仓 0 处 `LazyForEach`（`grep -r "LazyForEach" entry/src/main/ets/` 无命中）
- 全仓 0 处 `animateTo`/`transition`，交互反馈仅靠 `setTimeout`（`ItineraryPage.ets:163-167`）
