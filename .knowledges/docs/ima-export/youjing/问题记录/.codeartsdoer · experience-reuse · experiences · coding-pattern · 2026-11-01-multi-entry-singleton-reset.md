# 多入口场景下单例状态必须显式重置

## Scenario

当一个应用使用单例模式管理跨页面共享的"草稿"或"会话"状态（如旅行规划草稿、购物车、表单暂存），且有多个入口可以进入使用该状态的流程时，如果部分入口在进入前没有调用重置方法，用户从这些入口进入会带着上一次的残留数据，导致状态污染。

典型场景：用户完成了第一次规划流程（草稿中已填满数据），然后从另一个入口（如侧边栏按钮、Tab 页空态按钮）进入新规划，但草稿没有被清空，新流程中出现了上一次选的景点、住宿区域等残留数据。

## Key Signals

- 用户从某个入口进入流程后，发现表单中已有数据（不是默认值）
- 连续做两次规划/操作，第二次的结果受第一次残留数据影响
- 从不同入口进入同一流程，行为不一致（有的入口正常，有的带残留数据）
- 单例的 reset/fresh 方法只在部分入口被调用

## Essence

单例模式的 `get()` 方法只负责"获取或创建"，不负责"重置到初始状态"。一旦实例被创建并写入数据，后续所有 `get()` 调用都返回同一个带数据的实例。**每个进入使用该单例状态的流程的入口，都必须在进入前显式调用重置方法**。

这不是单例模式本身的缺陷，而是"多入口 + 单例状态"组合下的使用约束。单例保证了跨页面数据共享的便利性，但代价是每个入口都必须承担重置责任。

## Approach

1. **识别所有入口**：搜索所有调用 `enterPlanningFlow`、`pushPath` 进入流程首屏的地方，以及所有"新建"、"开始"按钮的 onClick
2. **在每个入口添加重置调用**：在进入流程前调用 `PlanDraft.fresh()` 或等效的重置方法
3. **在重置方法旁注释入口清单**：在 `fresh()` 方法的文档注释中列出所有需要调用它的入口，方便后续新增入口时检查
4. **代码审查检查项**：新增任何进入流程的入口时，必须检查是否调用了重置方法

正确用法对比：

```typescript
// ❌ 错误：只进入流程，不重置草稿
onClick((): void => {
  enterPlanningFlow('TripInput');
})

// ✅ 正确：先重置草稿，再进入流程
onClick((): void => {
  PlanDraft.fresh();
  enterPlanningFlow('TripInput');
})
```

## Faster Next Time

- 在单例类的重置方法注释中维护"调用方清单"，新增入口时对照检查
- 在代码审查 checklist 中加入"新入口是否调用了状态重置"这一项
- 考虑把 `fresh()` + `enterPlanningFlow()` 封装为一个函数，消除忘记调用的可能

## Applicability Boundaries

- **适用**：使用单例管理跨页面共享状态的应用、有多个入口进入同一流程的应用
- **不适用**：每次都创建新实例的场景（工厂模式）、状态不需要重置的场景（如只读配置）
- **注意**：如果流程支持"继续未完成的规划"（从草稿恢复），则不能无条件重置——需要先判断是否是"新建"还是"继续"

## Evidence or Examples

在 HarmonyProject2 项目中发现的具体案例：

- `PlanDraft` 是跨6个页面（屏2-屏6）共享的规划草稿单例
- 6个入口可以进入规划流程，但只有3个调用了 `PlanDraft.fresh()`：
  - ✅ YoujingStartPage.ets:77 — 有 `PlanDraft.fresh()`
  - ✅ TripsPage.ets:444/516/534 — 有 `PlanDraft.fresh()`
  - ❌ MinePage.ets:322-323 — 无 `PlanDraft.fresh()`
  - ❌ MapPage.ets:392 — 无 `PlanDraft.fresh()`
  - ❌ ExpensePage.ets:900 — 无 `PlanDraft.fresh()`
- 后果：从 MinePage、MapPage、ExpensePage 进入规划流程时，会带着上一次的 selectedSpots、selectedArea 等残留数据
