# 可由既有证据完整重建的聚合视图不要建表，改为读侧派生

## Scenario
产品要一个"勋章墙 / 城市套章 / 回顾统计"这类聚合视图，而底层已经存在带稳定主键、时刻、坐标、来源的打卡（事件）记录。直觉做法是升一版 schema 新建 badge 表并在写入时就地累加；另一种做法是读侧从证据表联表现算。

## Key Signals
- 聚合所需的每一个字段都能在证据行里找到（谁、何时、何地、来源、距离）。
- 写入路径有多个入口（手动打卡、到站打卡、未来可能的小艺入口），任何一处漏更新都会让聚合表静默失准。
- 页面上同一个聚合结果在多个位置消费（详情弹窗、回顾页、我的页、勋章页），各自口径不同就会互相对不上。

## Essence
聚合视图与证据表在竞争"谁是真相"。**只要聚合可 100% 重建、不需要防伪、也不需要服务端写入，就该只保留证据，聚合在读侧现算**。多加一张表带来的不是性能收益，而是一份必须同步维护的第二真相，以及一条遗漏就会出现的静默偏差。

## Approach
1. 先做三问判定：①能否只用已有证据 + 只读种子数据完整重建？②写入方是否已存在且不归本功能所有？③是否有防伪 / 跨端同步 / 证据可被删除的需求？①=是 且 ②=是 且 ③=否 → 选派生。
2. 读侧 DAO 只做 JOIN，不做写：`checkin JOIN activity ON a.id = trip_id || ':' || activity_id JOIN trip`，并按当前账号收口分区。
3. 聚合写成纯函数，明确合并键与四个折叠规则：`key = city + 分隔符 + normalizedName`；首次时间取 min、最近时间取 max、到访数累加、布尔能力取「任一次为真即真」、距离取最小值。
4. 对"没有父行的叶子记录"（如餐次打卡的主键是派生 key、没有 activity 行）靠 JOIN 自然落选，**并在聚合入口再加一道「查不到父行就丢弃」的兜底**，不依赖调用方自觉过滤。
5. 用例覆盖：输入顺序无关、空输入、重复到访合并、同一景点跨行程合并、叶子记录被过滤。
6. 把"为何不建表"写进 DAO 文件头，并给出重新建表的触发条件，避免下一个人当作遗漏而补表。

## Faster Next Time
- 评审遇到"新增聚合表"的提案，先问三个问题（可重建？写方可控？需防伪/同步？），比讨论性能更快定方向。
- 判断合并键时直接看证据行里哪些字段是"人可读且稳定"的；不要用自增 id 做合并键，否则跨行程同一景点会拆成多枚。
- 派生视图不要承载证据里不存在的信息（等级、经验值、稀有度）；这类字段一旦出现，说明该建表或改证据结构。
- 在测试里直接断言「同输入两次得到同结果、乱序输入结果相同」，派生实现的正确性主要靠这条。

## Applicability Boundaries
- 适用：成就/勋章/统计/排行榜快照等可重建视图；证据量级在千到万行、读侧聚合成本可接受。
- 不适用：需要防伪或离线校验、证据可能被删除或迁移、需要在写时低延迟返回聚合值、或证据量已大到读时聚合不可接受——这些场景应物化并接受同步成本。
- 判定条件变化（引入服务端同步、上架防伪）时应重新评估，而不是沿用当初的"不建表"。
- 与写入侧孤儿清理的边界：本经验允许「按设计无父行的叶子记录」在 JOIN 处落选，但要求聚合入口显式丢弃；若孤儿是删除/重建等写入动作造成的，则属数据一致性缺陷，应按 `2026-11-01-manual-cascade-and-orphan-evidence` 清理，不能继续靠 JOIN 落选掩盖。
