# 商业化改造端侧落地执行清单——契约先行、P0优先、逐层推进、一致性验证

## Scenario
一个端侧 LLM 应用从"个人项目"转向"上架收费"，需要在现有代码库上做大规模商业化改造：修发布前红线、加 BFF 中转、加权益系统、加付费墙、接 IAP。改动涉及 10+ 文件、跨端侧和后端两个项目。如果没有严格的落地顺序和验证机制，很容易出现"边写边改口径"、"新功能建在坏库上"、"改动后遗漏旧引用"等问题。

## Key Signals
- 在分析阶段就发现了 P0 级别的数据库迁移缺陷（`executeSql` 全部未 `await`，新建库必撞重复列），如果跳过 P0 直接做商业化基础设施，新功能会建在一个"新用户首次启动即坏库"的基础上。
- 改 `ApiConfig` 删 `API_KEY` 改 `BFF_BASE_URL` 后，如果 `LlmClient` 里还有旧字段引用，编译会失败或运行时拿到 undefined。
- 导出付费墙加在 `SharePage.exportIcs()` 和 `TripReviewPage.sharePoster()`，但文本分享（`shareSummary`/`shareNode`）不应加付费墙——付费墙只限制"落地使用"（导出到日历/海报），不限制"分享行程文字"。
- `PricingPage` 新建后必须注册到 `AppRouter.routerMap`，否则 `pushPath({ name: 'Pricing' })` 会回退到 `ComingSoonPage`。

## Essence
商业化改造的落地顺序是"契约先行 → P0优先 → 逐层推进 → 一致性验证"。先写契约文档固化方案，再修不依赖后端的 P0 红线，然后按 P1基础设施 → P2 UI 逐层推进，最后用 grep + 逐文件检查做一致性验证。每一步用 TodoWrite 跟踪状态，确保不跳步。

## Approach
1. **写契约文档**（`Docs/商业化方案.md`）：DDL、接口 Schema、错误码表、端侧改造清单、落地顺序。固化方案再动代码，避免边写边改口径。
2. **P0 修复**（不依赖后端，可立即做）：
   - RDB 迁移链：所有 `executeSql` 加 `await`，CREATE TABLE 去掉与 ALTER 重复的列。
   - 隐私闸门：同意前不构建 `mainTabs`、不调 `AccountStore.init`/DAO，同意后才 `bootstrap()`。
3. **P1 基础设施**（后端就绪后接线）：
   - `ApiConfig` 改造：删明文 Key，改 `BFF_BASE_URL` + 票据。
   - `LlmClient` 改造：加鉴权头 + `Idempotency-Key` + 401/402/429 错误码区分。
   - `ErrorCode` 新增云端错误码区段（6xxx）。
   - 新增 `EntitlementStore`：权益缓存到 preferences，`canExport()` / `canGenerate()` 判定。
4. **P2 UI 层**：
   - 新增 `PricingPage`：三档定价展示 + IAP 购买按钮。
   - `GeneratingPage` 接 402 分支跳 `PricingPage`。
   - 导出付费墙：`SharePage.exportIcs()` 和 `TripReviewPage.sharePoster()` 加 `canExport` 判定。
   - `AppRouter` 注册 `Pricing` 路由。
5. **一致性验证**：
   - `grep` 旧字段引用（如 `ApiConfig.API_KEY`、`ApiConfig.BASE_URL`）确认 0 处遗漏。
   - `grep` 所有 `store.executeSql` 确认全部带 `await`。
   - 确认新路由已注册到 `routerMap`。
   - 确认 `bootstrap()` 调用顺序正确（`DeviceTokenStore.init` → `DeviceActivator.activate` → `EntitlementStore.init` → `AccountStore.init`）。

## Faster Next Time
- 契约文档不是可选项——没有契约文档的改造一定会出现"做到第三步发现第一步的口径要改"的返工。
- P0 修复永远排在商业化基础设施前面——新功能建在坏库上等于白做。
- 改完 `ApiConfig` 后立即 `grep` 旧字段引用，不要等到全部改完再统一检查——越晚发现遗漏，修复成本越高。
- 导出付费墙只限制"落地使用"（导出/日历写入），不限制"分享文字"——付费墙放在用户已投入时间的环节，转化率最高。
- 新页面创建后，第一件事是注册到路由表——`pushPath` 到未注册的路由名会静默回退到 `ComingSoonPage`，很难排查。

## Applicability Boundaries
- 适用：端侧应用从"无商业化"转向"上架收费"的大规模改造，涉及多个模块和跨项目协调。
- 不适用：小规模功能添加或 bug 修复——这些不需要契约文档和分阶段推进。
- 契约文档的前提是方案已经过充分讨论和确认——如果方案还在探索阶段，先做原型验证再写契约。
- P0/P1/P2 的分层依据是"是否依赖后端"和"是否阻塞发布"——不是所有改动都能干净地归入某一层，边界模糊时优先归入更靠前的层级。

## Evidence or Examples
- 本次改造涉及 10+ 端侧文件 + 14 个 BFF 文件，按契约→P0→P1→P2→验证的顺序执行，无返工。
- P0 修复：`DatabaseHelper.ets` 20 处 `executeSql` 全部加 `await`，CREATE TABLE 去掉 `user_id`/`confidence`/`time` 重复列。
- 导出付费墙接入点：`pages/SharePage.ets:114`（`canExport` 判定 → `pushPath('Pricing')`）、`pages/TripReviewPage.ets:152`（同上）。
- 一致性验证：`grep "ApiConfig.API_KEY"` 返回 0 匹配，`grep "store.executeSql"` 返回 20 匹配全部带 `await`。
- `bootstrap()` 调用顺序：`DeviceTokenStore.init` → `DeviceActivator.activate` → `EntitlementStore.init` → `AccountStore.init` → `TripDao.listSummaries`。
