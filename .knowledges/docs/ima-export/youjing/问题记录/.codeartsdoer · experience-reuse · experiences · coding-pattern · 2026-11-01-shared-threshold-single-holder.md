# 跨屏共用的数值口径必须收口到单一持有者，其余位置只转发不复制

## Scenario
同一个业务口径被多个页面或多个模块同时消费：每日景点上限（3/4/6）、当日有效在场窗口（10 小时）、降水概率阈值（60%）、默认停留时长、日终时刻。若每处各写一份字面量，A 屏按 10 小时预选、B 屏却按别的窗口报「排太满」，用户看到的是两条互相矛盾的结论。这不是"要不要抽常量"的风格问题，而是口径所有权问题。

## Key Signals
- 同一个数字在两个以上无关文件里各自出现（窗口 600、日终 1439、默认停留 60、警告比例 0.8）。
- 代码注释里出现防御性说明：「别改回『最后结束 − 最早开始』」「唯一实现在 X，这里只是转发」——这类注释通常是历史上已经漂移过一次留下的疤。
- 一个模块明明是转发，却又把结果落成自己的 `static readonly` 常量（转发 + 复制混合），下游很难判断哪份才是权威。

## Essence
数值本身不是重点，"谁有权定义这个口径"才是。规则是：**一个业务口径只能有一个持有者，其余位置要么引用，要么用一行 static 方法转发；派生量必须由公式算出，不能再写字面量。**

## Approach
1. 用字面量搜索列出所有出现点，按业务语义分组：同义（都是"在场窗口"）还是巧合（都是 600 但一个是毫秒）。
2. 把持有者放在语义最贴近的领域文件里，而不是"最方便 import 的地方"：节奏档归 `model/PlanParams` 的 `PaceRule`，在场窗口归 `utils/DayLoad`，降水阈值归 `data/WeatherAdvisor`。
3. 其余位置改成薄转发：`PlanAutoPick.dailyCap(pace) { return PaceRule.dailyCap(pace); }`、`PlanAutoPick.SINGLE_DAY_WINDOW_MIN = DAY_WINDOW_MIN`。
4. 派生量写成公式而不是新字面量：`SIGHT_BUDGET_MIN = WINDOW_MINUTES - MEAL_MINUTES`。
5. 改完后加一条跨入口断言：同一个 pace 从两个调用方拿到的值必须相等；同一天同一个窗口在两屏上报出的等级必须一致。
6. 给持有者补一行取值理由与边界（"低于 8 小时误伤正常一天，高于 12 小时失去提醒意义"），让下一个人有依据而不是只能猜。

## Faster Next Time
- 评审时优先做一次数值字面量扫描（600 / 1439 / 0.8 / 60 / 3-4-6），比通读业务代码更快定位漂移面。
- 看到「别改回 X」的注释，直接当作"此处曾经双实现"的强信号去查另一份在哪。
- 判断是否该抽：问「改了这里，另一个页面是否会跟着变？如果不会，就不该有第二份」。
- 反向检查：派生量是否被写成字面量；转发方法是否又复制了一份常量。

## Applicability Boundaries
- 适用于有明确业务语义、且被两处以上独立消费的阈值、窗口、档位。
- 不适用于纯样式数值（间距、圆角、动效时长）——那类走 design token，不做业务口径收口。
- 若持有者与消费方跨进程或跨服务端，光靠代码内常量不够，还需要契约/配置层的单一来源；本经验只覆盖单进程内共享。

## Evidence or Examples
- 窗口唯一持有：`entry/src/main/ets/utils/DayLoad.ets:38`（`WINDOW_MINUTES = 600`），`utils/PlanAutoPick.ets:19,30-33,39-43` 全部转发并派生 `SIGHT_BUDGET_MIN`。
- 节奏档唯一实现：`model/PlanParams.ets:120-127`，`utils/PlanAutoPick.ets:31-33` 只转发。
- 阈值唯一持有：`data/WeatherAdvisor.ets:11,16`（`RAIN_MIN_PROB = 60`），被 `data/TripSignals.ets` 复用。
- 反例（仍然双份）：`data/SkipPlanner.ets:19-21` 与 `data/TripSignals.ets:72-73` 各写了一份 `DAY_END = 1439` / 默认停留 60 分钟；`utils/PlanAutoPick.ets:256` 与 `utils/Geo.ets:55` 的半径/通勤常数分散。
- 防御性注释即漂移证据：`utils/PlanAutoPick.ets:36-38`（「不再各写一份 600」）、`utils/DayLoad.ets:5-12`（「别改回跨度算法」）。
