# 网络失败一律降级为 null 时，必须同时补可观测信号与取消通道

## Scenario
产品里有一批"可选增强"能力：跳过某站后的智能重排、目的地天气。需求明确规定任何失败都不能阻塞主流程，于是客户端把未配置、网络错误、非 2xx、响应守卫拒绝、超时全部收敛成一句 `return null`，调用方拿到 null 就静默不展示。主流程确实不会卡住，但功能可能长期处于"从来没成功过"而无人知晓。

## Key Signals
- 多个 catch 分支最终都落到同一条 `Logger.warn(...); return null;`，日志里没有错误分类、没有耗时、没有重试次数。
- 配置为空（token 未设置）与网络抖动产生一模一样的表现：用户看不到功能，开发者看不到区别。
- 页面 `aboutToDisappear` 之后异步任务仍在跑；句柄只在 `finally` 里 `destroy`，没有中途放弃的手段。
- 重试写在循环里，固定次数、无延迟、无退避；单次读超时又很长，最坏等待时间 = 次数 × 超时。
- 计费类请求（LLM）的 token 用量只打日志，不落库、不聚合，事后无法回答"这次生成花了多少"。

## Essence
降级语义本身是正确的——可选能力不应拖垮主流程。问题在于"静默"是无意产生的副产品，而不是被设计过的目标。这里有三个不对称的缺失：**不可观测**使配置类错误永久隐藏（这是最高频的真实故障，不是网络抖动）；**不可取消**使页面生命周期结束后请求与账单继续存在；**无退避的重试**在服务端限流时反而放大失败面并翻倍成本。三者都不是功能缺陷，却决定了这个降级是否"可控"。

## Approach
1. 把失败分成两类并给不同信号：**预期降级**（功能关闭、配置缺失）打 info 一行；**意外失败**（网络、协议、守卫拒绝）打 warn，必须带错误码、目标、耗时、是否重试。
2. 加采样/聚合：同一原因首次出现立即打，后续按时间窗口聚合计数，避免"每次进屏都 warn"把日志淹掉。
3. 提供取消通道：让客户端返回 `{ promise, abort }` 或接受 `AbortSignal` / 请求句柄，页面销毁时调用 abort；取消后的结果不得再写入状态、不得计入重试次数、不得再触发副作用。
4. 设定超时预算而不是只设单次超时：`总预算 = 重试次数 × (connect + read) + 退避总和`，并对预算做上限断言；重试加指数退避与抖动。
5. 区分 `null` 与"可用但为空"：前者表示依赖不可用（不出该行），后者表示查询成功但没有数据（可出空态），不要用一个值表达两种语义。
6. 计费型请求把 `usage` 落成本地统计（按会话/天聚合），至少让"成本"成为可查询的量，而不是只能翻日志。
7. 在代码评审清单里加一条固定项："每个 `catch → return null` 是否留下了可区分的痕迹？"。

## Faster Next Time
- 看到先 `catch` 再 `return null`，先问三句：**配置错误能被看见吗？页面退出后请求还在跑吗？重试总共要等多久？** 三问都能答，降级才算闭环。
- 反直觉点值得记住：这类组件的线上"故障"多数不是网络问题，而是配置从未正确设置——所以首条日志必须能区分"没配"和"配了但请求失败"。
- 评审时把"是否有 abort"和"是否有总超时预算"当作硬性条件，比事后加埋点便宜得多。

## Applicability Boundaries
- 适用：可选增强型外部依赖（推荐、天气、翻译、A/B、非关键 AI 能力），以及任何"失败不阻塞主流程"的客户端调用。
- 不适用：核心链路（登录、支付、下单）——那里不应静默降级，而应显式失败并给出可操作提示。
- 若运行时没有取消原语（部分 SDK 只提供一次性请求），退而求其次：结果回来时检查生命周期标志并丢弃，同时把单次超时压到可接受范围，并在文档里写明"无法真正取消，仅丢弃结果"。
- 本经验聚焦降级可观测性与取消通道的通用模式，不涉及商业化架构决策——后者见 `2026-11-01-end-side-llm-monetization-bff`。

## Evidence or Examples
- 全异常收敛为 null：`entry/src/main/ets/ai/ReplanClient.ets:59-72`（网络、非 2xx、守卫拒绝、超时统一 warn 后返回 null）；配置为空直接返回 null 在 `ReplanClient.ets:22-25`。
- 天气同样静默：`entry/src/main/ets/common/weather/WeatherClient.ets:19-50` 与 `entry/src/main/ets/data/WeatherStore.ets:66-79`，失败即不出天气行。
- 固定重试无退避：`entry/src/main/ets/ai/LlmClient.ets:366` 固定两次，失败抛 `TRIP_GENERATE_RETRY_EXHAUSTED`（`LlmClient.ets:386`）。
- 无取消：`entry/src/main/ets/ai/LlmClient.ets:347-349` 句柄只在 `finally` 里 `destroy`；页面侧 `entry/src/main/ets/pages/GeneratingPage.ets:60-64,97-99` 的 `cancelled` 标志只丢弃结果，请求仍会跑满读超时。
- 超时口径：`entry/src/main/ets/common/config/ApiConfig.ets:88-93`，LLM 连接 10s / 读 120s，重排连接 2s / 读 6s——两者叠加固定重试后，LLM 最坏等待约 4 分钟。
- 成本不可查：`entry/src/main/ets/ai/LlmClient.ets:311-322`，token 用量仅写入日志，无持久化与汇总。
- 反例（做得对的部分）：重排失败后 `entry/src/main/ets/pages/OnTripPage.ets:367-381` 会提示"重排失败，行程未改动"并保持原状，说明"降级要留痕"的原则在 UI 层已被遵守，只是网络层没有对齐。
