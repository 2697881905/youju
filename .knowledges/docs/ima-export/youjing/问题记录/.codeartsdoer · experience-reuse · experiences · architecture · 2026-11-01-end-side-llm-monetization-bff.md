# 端侧 LLM 应用商业化改造——控制面在云、数据面在端，Key 出端走 BFF 代理

## Scenario
端侧 LLM 应用（行程生成、文案创作等）需要从"个人项目"转向"上架收费"。当前架构：API Key 明文写在端侧配置文件里（靠 `git update-index --skip-worktree` 防误提交），LLM 请求直连供应商端点，token 用量只打日志无持久化，无账号、无配额、无防刷。上架需要解决四个问题：Key 安全、用量控制、收费机制、合规备案。

## Key Signals
- `ApiConfig.ets` 里明文 `API_KEY: 'sk-5743...'`，HAP 可反编译提取。
- `skip-worktree` 极易被破坏：重新克隆、`git add -f`、切分支 merge 都会让明文重新入库。
- `LlmClient` 重试固定 2 次且无延迟、无退避，弱网下两次串行最长 240 秒。
- 请求不可取消：`cancelled` 标志只丢结果，不中止 HTTP 请求。
- 无幂等键：弱网重试会变成重复请求，接上计费后就是重复扣费。
- token 用量只打日志（`LlmClient.ets:311-322`），没有成本汇总或用量追踪。

## Essence
端侧 LLM 应用商业化的核心架构决策是"控制面在云、数据面在端"：账号、权益、额度、计费、Key、模型路由放在云端（BFF）；行程内容、打卡、账本等用户数据继续留在设备本地 RDB。这样既保护了"本地优先"的产品定位，又获得了收费所需的控制能力。Key 出端是安全补丁而非架构选型——一个只做转发的云函数能同时解决 Key 安全、用量追踪、模型切换不发版、Prompt 灰度四件事。

## Approach
1. **Key 出端**：删除 `ApiConfig` 中的明文 `API_KEY` 和 `BASE_URL`，改为 `BFF_BASE_URL`（指向自建云函数）+ `DEVICE_TOKEN`（设备票据，由 `/v1/device/activate` 获取）。端上不存任何 LLM 供应商的密钥。
2. **幂等键贯穿重试**：`generateTrip` 生成一个 `Idempotency-Key`（UUID），重试时复用同一个 key，服务端按 key 去重。`LlmTransport.complete` 签名加 `idempotencyKey` 参数。
3. **错误码区分**：401→票据失效（需重新激活）、402→额度不足（跳付费引导页）、429→限流（提示稍后重试）。不可重试的错误（401/402/403）不进入重试循环。
4. **预扣→结算→回滚**：服务端在转发 LLM 前预扣额度（reserved），成功后 committed（扣 1），上游超时/5xx 后 released（不扣），客户端主动取消且请求已发出也 committed（成本已发生）。
5. **端侧改动最小化**：只改 6 处——`ApiConfig`（删 Key 改 URL）、`LlmClient`（加鉴权头+幂等键+错误码区分）、新增 `EntitlementStore`（权益缓存到 preferences）、新增 `PricingPage`（付费引导页）、`ErrorCode`（新增云端错误码区段）、`GeneratingPage`（接 402 分支跳 PricingPage）。
6. **数据面不动**：行程、打卡、账本继续走本地 RDB，DAO 的 `user_id` 分区设计已经天然支持多账号，不需要重写。

## Faster Next Time
- 看到 `ApiConfig` 里有明文 Key，直接判定为 P1 安全缺陷，优先级高于任何功能开发。
- `skip-worktree` 不是安全措施，只是防误提交的便利工具——评估 Key 安全时不要把它算作防护层。
- 端侧 LLM 应用接计费时，幂等键是第一个要加的东西，不是最后一个——没有幂等键的计费系统在弱网下一定会重复扣费。
- 重试逻辑要区分"可重试"（网络超时/5xx/429）和"不可重试"（401/402/403），不可重试的错误进入重试循环只会浪费时间和 token。
- 控制面/数据面分离的判断锚点：云端看到的只是随机 UUID 和时间戳，不含任何行程内容——如果云端能看到行程内容，就突破了数据面的边界。

## Applicability Boundaries
- 适用：端侧 LLM 应用需要上架收费，且产品定位是"本地优先/隐私优先"的场景。
- 不适用：本身就有自建后端的应用（不需要再做 BFF 分离决策）；或纯离线应用（不涉及 LLM 调用，不需要控制面）。
- "控制面在云"的最小实现是一个云函数（5 个接口），不是一整套微服务——不要过度设计。
- 如果产品定位转向"多人协作/实时同步"，则不再是加控制面的问题，而是需要重新做架构评审。
- 华为应用市场分发的虚拟服务通常必须走华为 IAP，不能自己接第三方支付——具体条款以上架时最新协议为准。
- 本经验聚焦商业化架构决策（控制面/数据面分离、Key 出端），不展开降级可观测性与请求取消的实现细节——后者见 `2026-11-01-null-fallback-needs-observability-and-cancel`；skip-worktree 的局限性详见 `2026-11-01-skip-worktree-not-a-secret-boundary`。
