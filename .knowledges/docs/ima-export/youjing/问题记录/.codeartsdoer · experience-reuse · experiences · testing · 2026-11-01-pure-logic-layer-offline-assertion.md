# 把可测业务逻辑放在无平台依赖的纯函数层，测试才不必依赖设备上下文

## Scenario
设备侧单测框架的上下文拿不到数据库、偏好存储等能力（写这种测试要么起不了库，要么被环境卡住）。结果是：业务逻辑一旦写在 DAO 或页面里，就永远测不到；而为了可测把逻辑抽出来，又会遇到"抽到哪一层、I/O 怎么留"的分歧。

## Key Signals
- 测试里大量 `new` 出来的只有 plain object，没有任何 `Context` / RDB / 系统 Kit；而页面里同样的规则没有任何断言。
- 注释里出现「ohosTest 的上下文拿不到 RDB，放在 DAO 里就等于测不到」——这是分层选择留下的直接证据。
- 覆盖率看着不错，但真正容易出错的编排（节流窗口、订阅竞态、撤销状态）全在页面文件里，测试目录内零引用。

## Essence
可测性不是写测试时才获得的，而是分层时就决定的。判据只有一条：**这个模块能不能只 import 数据模型与纯计算、不 import 平台 Kit？** 能，就可以离线 tsc + 断言；不能，就必须把"决策"从"编排"里拆出来，让 I/O 留在薄壳里。

## Approach
1. 立规则并写进文件头：纯逻辑文件「禁依赖 @kit，可离线 tsc + 断言」，import 白名单只有 `model/` 与同层 `utils/`。
2. 三层落位：纯逻辑（`utils/`、`data/` 内无 I/O 部分）→ 平台适配（`common/location`、`data/*Dao`）→ 编排（`pages/`）。只有第一层进单测。
3. 把页面里的"判定"改造成纯函数 + 普通结构体输入：用一个 `SignalContext { isToday, nowMin, fix, checkedIds, currentKey, weather }` 承载全部输入，页面只负责取值与渲染。
4. 抽不动就先抽计算再包 I/O：需要 `Context` 的只有查询那一段，查询结果当作数组入参传给纯函数（如聚合、排序、分箱）。
5. 测试矩阵固定六类：空输入；乱序输入结果不变；边界值（恰好等于阈值两侧）；跨天/跨年；幂等（同输入两次同输出）；失败分支（残缺字段、脏 JSON）。
6. 交付时同时给出"仍在页面里的判定清单"（如 30 分钟静默窗口、Watcher 启停竞态、撤销快照失效），把它当剩余风险说明，而不是用覆盖率数字抹平。
7. 检查副作用与入参别名：纯函数不得原地修改入参（本项目中回填类函数就会直接改 `trip/activity`），排序函数在空目标时若原样返回入参数组，调用方后续修改会污染源数据。
8. 把分层规则做成可执行检查而不是口头约定：用一条 grep/CI 断言纯逻辑目录不出现 `@kit` import，纯函数测试文件不 import `Context`，让"测不了"在评审阶段就暴露。

## Faster Next Time
- 写新逻辑前先问一句「它能不能只吃一个 interface、吐出另一个 interface」，能就直接放纯逻辑层，不用等测试失败才发现测不了。
- 评审时用一条 grep 代替通读：纯逻辑目录里出现 `@kit` import 就是分层被破坏的信号。
- 判断"这段该不该抽"的标准是输入是否可枚举，不是代码行数。
- 覆盖率盲区用"页面里还有哪些 if 分支决定用户可见结论"来盘点，比看行覆盖率有效。

## Applicability Boundaries
- 适用：规则密集、可枚举输入的业务逻辑（选点、负载、信号判定、派生聚合、预算计算）。
- 不适用：必须真机或系统服务的能力（定位订阅、系统围栏、推送、权限弹窗）。这类只能测状态机与参数构造（如采样间隔、优先级枚举），不能断言系统实际行为。
- 抽取有成本：一次性脚本或纯 UI 布局逻辑不必强行分层；判据是"会不会被第二处消费或被判定为正确性关键"。
- 分层只解决"能不能测"，不解决"口径是否一致"：同一个阈值仍需按单一持有者收口（见 `2026-11-01-shared-threshold-single-holder`），否则三层结构也挡不住跨屏结论矛盾。

## Evidence or Examples
- 纯逻辑声明与依赖白名单：`entry/src/main/ets/utils/BadgeBoard.ets:1-2`、`utils/DayLoad.ets:1-2`、`utils/TripIntentParser.ets:1-7`、`utils/CategoryBudget.ets:1-7`（明确为"可离线断言"才单独成文件）。
- 平台能力被收在单层：`common/location/ArrivalWatcher.ets:1-10,30-35`。
- 判定输入被外置成结构体：`data/TripSignals.ets:31-51`。
- 单测规模与覆盖对象：`entry/src/ohosTest/ets/test/` 下 28 个 `*.test.ets`，覆盖意图解析、选点、负载、三信号、SkipPlanner、勋章/套章、回顾等。
- 未覆盖的编排与副作用：`pages/OnTripPage.ets:97-98,749-773`（30 分钟静默与忽略逻辑）、`:628-659`（订阅启停）；原地修改入参见 `utils/TripEnrich.ets:49-77,85-109`；入参别名风险见 `utils/PlanAutoPick.ets:126-128`。
