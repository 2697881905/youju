# 无外键级联时删除聚合根必须倒序手工清理，重建子行会留下指向旧行的证据孤儿

## Scenario
行程、订单、文档这类聚合根，下有日程/节点/明细等子表，再往下有打卡、记账、附件这类"引用子行 id 的证据行"。数据库没有外键，或者团队为了迁移与性能不启用外键。删除与编辑都由应用代码负责维护引用完整性。

## Key Signals
- `DELETE FROM 主表` 之后子表行数不减少。
- 编辑保存后，历史打卡/记账仍带 `trip_id`，但 `activity_id` 已找不到对应节点。
- DAO 注释里出现"查不到父行会在 JOIN 处自然落选"——这是在承认孤儿存在，并把它当成正确性证明。
- 删除逻辑散落在多个 DAO，顺序不统一，也没有统一事务包裹。

## Essence
没有 FK 时，引用完整性从数据库职责变成应用职责，而应用有两个必漏点：一是删除只删主表；二是编辑用"删子表 + 重建"实现，新子行换了 id，下游证据行的外键就悬空。JOIN 落选只是让孤儿在页面上不可见，数据仍然占空间、参与全表统计，并可能在将来同步时被上传。孤儿不是渲染问题，是数据一致性问题。

## Approach
1. 先画依赖图：列出聚合根的所有子表，以及所有"引用子行 id 的证据表"。
2. 删除按依赖倒序在单一事务内执行：证据表 → 明细 → 子表 → 日程 → 主表；主表删除语句同时带分区键。
3. 编辑优先做 upsert/diff，保留稳定 id；必须重建时，在同一事务内清理指向被删节点的证据行，或把证据改为软引用并保留名称/坐标快照。
4. 增加一次性启动清理：删除父行不存在的孤儿行，并记录清理数量。
5. 验证：删除后逐表 count 归零；编辑替换节点后，旧 `activity_id` 的打卡/记账不再残留。

## Faster Next Time
- 评审删除逻辑先问三件事：有哪些子表、哪些表引用子行 id、是否在同一事务里。
- 看到"delete children then rebuild"就直接去查下游证据表，这是孤儿高发点。
- 把"JOIN 自然落选"当成孤儿存在的告警，而不是免于清理的理由。
- 对本地优先应用，孤儿还会进入导出与未来的同步 payload，优先级应高于普通展示缺陷。

## Applicability Boundaries
- 适用：无外键或未开启外键的本地库/文档库；聚合根整存整取、子行 id 会被重建。
- 不适用：数据库已启用 `ON DELETE CASCADE` 且所有写入都经过它；或证据行需要长期保留用于审计/历史——此时应改软删除或快照，而不是物理删除。
- 一旦引入服务端同步，孤儿会被同步出去，清理必须提前到同步之前完成。
- 与结构迁移经验的边界：重建表 / 改约束这类 DDL 迁移也会产生孤儿，迁移验证除了校验表、列、索引，还要把「子表与证据行无孤儿」当成独立断言，见 `2026-11-01-schema-migration-dual-path-verification`。
- 与读侧派生经验的边界：读侧 JOIN 落选只适用于「按设计就没有父行的叶子记录」，且聚合入口必须显式丢弃并计数；写入侧（删除聚合根、删子行重建）产生的孤儿不属于这一类，必须物理清理或改软引用。两者外观相同、责任不同，见 `2026-11-01-derive-view-over-new-table`。

## Evidence or Examples
- 手工级联删除顺序（checkin → expense → meal → activity → trip_day → trip，单事务）：`entry/src/main/ets/data/TripDao.ets:306-314`。
- 保存时先删 activity/meal 再按 days 重建：`TripDao.ets:55`、`TripDao.ets:291-313`。
- 孤儿仅在 JOIN 处落选、数据仍保留：`data/BadgeDao.ets:22` 注释。
- v9 的一次性历史孤儿清理：`data/DatabaseHelper.ets:142-148`。
- 全仓无 `FOREIGN KEY`/`REFERENCES` 命中（本次分析结论）。
