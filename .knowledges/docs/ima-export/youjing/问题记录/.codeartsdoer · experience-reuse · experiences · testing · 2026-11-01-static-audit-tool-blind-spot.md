# 静态审计尺需要反证用例——"全绿"不等于"没问题"

## Scenario

项目设有多把静态审计尺（Python 脚本），用于在 CI 中自动检查代码是否遵守设计契约（颜色 token、字号 token、几何值、无障碍命名等）。审计尺长期报告"0 偏差"，团队据此认为相关规范已全面落实。

## Key Signals

1. `audit_geometry.py` 报"偏差 0 项"，但代码中存在大量裸写几何值（`ItineraryPage.ets:676` 写 `height(22)`、`:832-833` 写圆点 `22`、`:1244` 写 `28`；`ExpensePage.ets:376-377` 写 `8`、`:382` 写 `40`、`:405` 写 `84`）。
2. `audit_a11y_name.py` 只查 10 类语义控件的可访问性名称，但可点击的 `Row`/`Column` 容器（如 `ItineraryPage.ets:727-730`）未在覆盖范围内。
3. 其中 `8` 已有 `LayoutTokens.activityDotSize`（`LayoutTokens.ets:87`）、`44` 已有 `minTouchTarget`（`:121`），属可消除的撞值——审计尺本应报红却没报。

## Essence

审计尺的"全绿"只代表**被尺子覆盖到的范围内**没有问题，不代表**整个代码库**没有问题。尺子本身存在两类盲区：

1. **值域盲区**：只校验"已在具名 token 表内的值是否偏差"，不校验"是否存在未进表的裸写值"。裸写值根本不在审计范围内，自然不会报偏差。
2. **类型盲区**：只覆盖特定控件类型（如 10 类语义控件），未覆盖的类型（如可点击的 Row/Column）即使有问题也不会被检查。

"全绿"的真正含义是"尺子能看到的都合规"，而不是"所有代码都合规"。**尺子本身需要定期反证**——故意写违规值，看尺子是否报红，否则尺子可能已经失效。

## Approach

1. **为每把审计尺编写反证用例**：在测试目录中故意写一段包含裸写几何值、未命名可点击容器的代码，运行审计尺，必须报红。如果报绿，说明尺子有盲区，需要修复尺子。
2. **审计尺的覆盖范围必须文档化**：在尺子脚本头部明确列出"本尺检查什么"和"本尺不检查什么"，避免使用者误以为全覆盖。
3. **值域审计改为"白名单模式"**：不是"检查具名值是否偏差"，而是"检查所有出现的数值是否都在具名表中"——任何不在表中的裸写值都报红。
4. **类型审计改为"全覆盖声明"**：列出所有需要检查的控件类型，未覆盖的类型在报告中显式标注"未检查"。

## Faster Next Time

- 新增审计尺时，同步写一条反证用例（故意违规的代码片段 + 期望报红的断言）。
- 审计报告不要只输出"偏差 N 项"，还要输出"未检查的控件类型 X 种"和"未进表的裸写值 Y 个"。
- Code review 时，不要因为"审计全绿"就跳过几何值和可访问性检查——审计尺的盲区需要人工补位。

## Applicability Boundaries

- **适用**：所有使用静态脚本做代码规范审计的项目，尤其是审计尺只做"正向检查"（检查已知值是否偏差）而非"反向检查"（检查未知值是否存在）的场景。
- **不适用**：使用编译器或类型系统做强制约束的场景（如 TypeScript 的 `as const`、ESLint 的 `no-magic-numbers` 规则），这些工具天然是白名单模式。

## Evidence or Examples

- `audit_geometry.py` 报"偏差 0 项"，但 `ItineraryPage.ets` 中至少 7 处裸写几何值（22、28、8、40、84、56），其中 `8` 和 `44` 已有对应 token。
- `audit_a11y_name.py` 只查 10 类语义控件，`ItineraryPage.ets:727-730` 的可点击 Row 未被覆盖。
- `audit_colors.py` 和 `audit_type.py` 是有效的正向+反向审计（48 件 0 偏差、Text 0 / 图标 0），可作为其他尺子的改进参考。
