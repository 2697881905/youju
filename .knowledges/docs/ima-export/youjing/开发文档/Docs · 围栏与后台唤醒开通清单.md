# 围栏与后台唤醒开通清单（有径）

> 2026-10-27 起草，**2026-10-30 更新：原先预设的两道闸门已合流成一个**。
> 运营团队明确回复：申请已由 AGC 受理、目前审核中，通过后会收到系统通知、服务随即可用；
> 邮件渠道不单独开通。所以现在只剩「等 AGC 审核结果」一件事，材料与复测清单留档在此。

## 〇、结论先行（为什么现在还得等）

真机探针（Pocket 2，2026-10-27，分支 `spike/geofence-probe`）实测：

| 步骤 | 结果 |
|---|---|
| 定位授权弹窗（仅使用期间） | `authResults=[0,0]`，通过 |
| 前台 `on('locationChange')` | 正常出回调（室内 acc≈237m） |
| `addGnssGeofence` r=100 / r=200 / 边界围栏 | **全部注册成功**（fenceId 4–9），无参数闸门 |
| 围栏内 DWELL 25s（loiterTimeMs=10s） | **0 次事件回调** |
| 圆心压在定位误差带上的边界围栏 60s | **0 次事件回调** |

即：**注册 API 不闸，监测引擎不跑**。2026-10-30 官方回复把口径讲清了：监测服务的开通跟着
**AGC 的申请**走，审核通过前引擎不会工作——不需要另外邮件单独开通。
在审核结果出来前，行中/打卡走 **T1 降级路径**：屏15 存活期间用前台
`locationChange` 判进入半径（已验证可用），开通后升 T2 系统围栏。

> 2026-11-09 补充：**实况窗已被 AGC 驳回**——实况窗仅支持固定场景，行程/景区到站不在
> 开放范围（官方场景表明确把「景区推荐/打卡」列为 `CHECK_IN` 的不适用案例）。实况窗不再
> 作为 P5 的交付或验收依赖；P5 收敛为「系统围栏事件 + 本地通知」，代码已移除。

## 三、开通后复测清单（复用探针分支）

1. `git checkout spike/geofence-probe` → 构建 → `aa start … --ps geoprobe 1`（授权已持久化）；
2. 判据 A（前台）：围栏内 ≥15s 应出现 `fence[r100-inside] 事件 … DWELL`；
3. 判据 B（后台）：注册后按 Home 退后台 90s 再回前台，hilog 应含后台时段的事件时间戳
   （此判据同时验证「围栏后台唤醒」是否随同一审核一并生效）；
4. 判据 C（半径）：r=100 注册与触发均正常后，再验 r=300 室外步行进入的 ENTER 时延；
5. 复测通过 → 切片 2 升 T2：`GeofenceManager`（独立 Manager，不放页面）+ 勋章落库；
   复测不通过 → 保持 T1 并在本文登记失败形态。

## 五、代理提醒（P4）是第二道 AGC 闸门（2026-11-09 补）

P4 原判断是「端侧、不需 AGC」，真机实测推翻了这个前提：

| 事实 | 证据 |
|---|---|
| `publishReminder` 被管控 | 系统日志 `VerifyCloudCapability failed ... capability = reminder_capability` |
| App 侧错误码会伪装 | 管控时 App 只拿到 `1700002 The number of reminders exceeds the limit`，不是 `ungranted capability` |
| 排除真超限 | 本 App `getAllValidReminders()` 为 0 条时仍报 1700002 |
| 权限本身不是问题 | `ohos.permission.PUBLISH_AGENT_REMINDER` 已声明，SDK 定义为 `normal` + `system_grant` |
| 管控范围 | 官方文档：手机/平板/PC 有管控，智慧屏/穿戴无管控 |
| 官方替代 | Calendar Kit 写入带 `reminderTime` 的日程 |

代码侧已按这个证据修正：`TripReminder.syncTrip` 发布前读取本 App 有效提醒数，
`1700002` 且有效数为 0 时判 `blockedByCapability=true`；有效数非 0 才判
`blockedByLimit=true`。真机 `--ps remindsyncprobe 1` 已复验：
`blocked=true blockedLimit=false`。

**开通路径**（官方文档「代理提醒开放能力申请」）：

1. AGC → 项目设置 → 开放能力管理 → 「代理提醒」→ 申请；
2. 应用分类需属于旅游类等支持类型，场景填「行程提醒」；
3. 8 个工作日反馈；通过后勾选能力开关并保存；
4. **必须重新生成 Profile 并手动签名**，否则调试/发布包仍拿不到权益。

**申请原因（可直接粘贴）**：

> 有径（com.youjing.app）是旅行行程规划与行中陪伴应用，应用分类为旅游类。
> 用户在行前生成逐日行程后，需要在出发前一天、预约节点提前 N 天、以及每日
> 07:30 收到行程提醒；应用退后台或锁屏时仍须由系统代理按时提醒。该场景属于
> 「行程提醒」，不涉及广告、营销、优惠券或直播预约。申请开通代理提醒能力，
> 用于旅行场景的定时行程提醒。

**材料清单**：AGC 应用信息页（证明旅游类分类）、`module.json5` 权限声明页、
提醒开关/行程提醒文案截图。申请通过后重签 Profile，`TripReminder` 无需改代码。

代码侧 `TripReminder` 已就绪（出发前 TIMER / 预约提前 CALENDAR / 晨间 CALENDAR）；
审批和重签完成后直接真机复验锁屏，不需要改代码。未通过前若必须锁屏提醒，
只能退回 Calendar Kit，但当前日历写入受 `canExport` 付费墙约束，是否接受这个降级需产品确认。

官方依据：[代理提醒(ArkTS) · 约束与限制 / 开放能力申请](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/agent-powered-reminder)。

## 六、杨凌坐标校准（2026-11-09 补）

到站半径只有 300m，种子坐标是街道/村镇级近似值；行中验收前必须先校准。

- 探针：`aa start -a EntryAbility -b com.youjing.app --ps coordprobe 1`
  - 读一次 GPS，打印 `fix lat/lng/acc` 和最近 3 个种子站的距离/坐标。
  - 站在景点入口或核心点，尽量等到 `acc ≤ 100m` 再记录。
- 判读：最近站距离 >300m 且明显偏离（如 400m+），把探针输出的 `fix` 回填到
  `entry/src/main/resources/rawfile/spots_yangling.jsonl` 对应站的
  `latitude` / `longitude`，再重跑同一探针确认距离落到 300m 内。
- 已验探针链路（2026-11-09，设备在杨凌但不在站内）：
  `fix lat=34.239187 lng=108.039432 acc=100m`，最近川云关 1453m、教稼园 1482m。
  说明种子与当前位置同区，探针可用；逐站回填仍需现场完成。
