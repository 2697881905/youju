# 证据驱动的代码审查

## 适用场景

- 用户点名一组文件，要求 very thorough 分析并逐条回答架构/算法/质量问题。
- 硬性要求：每条结论附 `路径:行号`、限定字数、明确"不要修改任何文件"。
- 需要判断"是否真的"（真的不建表？真的纯函数？真的去重/打散？）。

## 工作流

1. **并行读点名文件**：每批 4–6 个 `Read`，不要串行逐个读；先建立模块全貌。
2. **追踪点外决策点**：阈值来源、静默窗口、撤销、生命周期常落在调用方页面/DAO。
   用 `Grep` 搜关键符号（如 `TripSignals.suggest`、`ArrivalWatcher`、`skipSnapshot`、常量名），
   再用 `Read` 的 offset/limit 只读周边 100–250 行，不整文件重读。
3. **验证断言而不是相信注释**：
   - "不建表"→ 查 DAO 的 SQL/JOIN 与 schema，确认数据是否派生。
   - "阈值唯一"→ grep 同一数字是否在多文件重复定义。
   - "可测试"→ 查 `entry/src/ohosTest/ets/test/` 是否有对应测试；页面内逻辑通常测不到。
   - "去重/打散/聚类"→ 找实际循环与集合操作，没有就明确说没有。
4. **交叉核对注释与实现**：头注释声明 vs 实际入参/分支，标记文档漂移（这是高价值发现）。
5. **按用户问题编号输出**：先声明路径前缀（如"路径均相对 `entry/src/main/ets/`"）省字数；
   每条结论后紧跟 `relative/path.ets:start-end`；不确定的行号先 grep 再写，禁止猜测。

## 全项目全景盘点（整库级，不是单模块）

用户要求"全面梳理/深入分析整个项目"并列出 9 类维度时，不要单个 agent 串行通读全库（两万行级会撑爆上下文）。按维度切分并行取证：

1. **主 agent 先做全局勘察（不派发）**：根目录、README、`build-profile.json5` / `oh-package.json5` / `module.json5`、最近 20 条 `git log --oneline`、源码行数与各目录文件数。这一步定"项目阶段"和"技术栈真实版本"，也避免子 agent 重复劳动。
2. **按内聚维度派 4–5 个 explore 子 agent**，典型切分：①启动入口 + 路由 + 主链路 ②AI/网络层 ③数据持久化层 ④纯业务逻辑（按项目的业务分段）⑤UI + 设计系统。每个提示词必须带三条硬约束：
   - "务必给出 `文件路径:行号` 证据"
   - "控制在 800–900 字以内"
   - "不要修改任何文件"
   并给该维度**具体追问**（"初始化顺序是什么、失败怎么降级、有没有 N+1、阈值定义在哪"），不要只写"分析一下"。
3. **子 agent 返回后，主 agent 必须复核三类断言**（本工作流的命门）：
   - **"未使用 / 失效 / 死代码"类**：grep 全仓再判。例：子 agent 因 `consentAgreed` 声明后未使用而推断"隐私闸门失效"，实际 `consentDialog.open()` 在 `aboutToAppear` 正常打开；真正的问题是"弹窗只做视觉遮挡、同意前已读取本地数据"。把子 agent 的"失效"改写成准确的"缺口"。
   - **"没 await / 没校验 / 无锁"类**：`sed -n` 读函数体确认，并推完整后果链（未 await 的 DDL + 紧接着写 version = 迁移失败被吞且永不重试；若 CREATE 已含列又 ALTER 同名列 = 新建库必撞 duplicate column）。
   - **"O(n) / 全表扫 / 无缓存"类**：看真实 SQL、索引定义、调用频率再下结论，别只看函数名。
   复核成本只有一两次 grep/sed，但能防止把错误结论写进报告。
4. **横向对比落到"结构性短板"**：不要罗列功能表。固定对比维度：数据丰富度、隐私、离线可用、成本、可运维性、多端一致性、平台契合、延迟。最后各给一句"不可替代优势"与"最大结构性短板"。
5. **建议分级并给验收方式**：P0（发布阻塞：数据损坏、合规）、P1（首版前：安全、成本、正确性）、P2（性能与可维护性）、P3（架构演进）。每条附"依据 `path:line` + 怎么验"，禁止只写"建议优化"。
6. **报告尾部放证据索引表**：关键结论 → 证据位置，便于用户抽查与下一轮只读复核。

## 审查清单

- 魔法数字：是否具名、是否跨文件重复（`DAY_END`、默认停留、窗口分钟）。
- 函数长度：超过 ~60 行重点标注，给出起止行。
- 纯函数：是否原地修改入参（`trip/activity`）、是否返回入参别名、是否依赖全局状态/时间。
- 生命周期与竞态：订阅/退订顺序、token 防旧回调、前后台是否停订。
- 算法真实行为：排序键、候选池大小、复杂度、缺失的"去重/分桶/打散"。
- 降级路径：空输入、缺坐标、非法日期、上游失败是否静默且可解释。
- 测试覆盖缺口：纯逻辑有测、页面编排无测时明确指出。

## UI / 设计系统审查要点

被审对象是页面 + token 目录 + 组件 + 响应式工具时，按这六问取证，每问都要落到行号：

1. **token 分类与真实覆盖**：数 `design/` 下的文件数并各自列封闭集数组（如 `ALLOWED_FONT_SIZES`、
   `ALLOWED_SPACINGS`、`ALLOWED_RADII`）；封闭集数组的存在只证明"定义了"，不证明"用上了"。
2. **"禁止裸样式值"是否成立**：分别统计裸 `fontSize(数字)`、`width/height/padding/borderRadius(数字)`。
   常见结论是"字号干净、几何脏"——然后去 token 文件里找**撞值**（裸写 8 而 `activityDotSize=8` 已存在、
   裸写 44 而 `minTouchTarget=44` 已存在），这才是"该用未用"的硬证据，而不是笼统说"有裸值"。
3. **深浅色档**：对比 `resources/base/element/color.json` 与 `resources/dark/element/color.json`
   的同名条目数；再看 token 文件是否**只导出 `$r` 引用**（= 页面零分支）；最后 `grep isDarkMode`
   看它到底用于配色还是仅用于材质/阴影门控，两者含义完全不同。
4. **组件化**：列出 `components/` 全部组件及其覆盖的能力（按钮/分段/外壳/弹窗/地图），
   再找**未组件化的重复结构**——同一段 `surfaceElevated + radius + padding` 卡片在多页各写一份、
   `bindSheet` 面板全部内联而只有少数 `@CustomDialog`。统计 `@Builder` 数量与 `@Styles/@Extend` 数量
   （后者全仓 0 是"样式复用为零"的判据）。
5. **状态与响应式**：`@State` 逐个文件计数并判断能否聚合；`@Link` 找双向绑定点及其 `@Watch` 级联；
   `aboutToAppear` 是否有串行 await 重活（有 `onShown` 替代的页面反而是正面范例）。
   响应式要区分"有映射函数"和"有消费点"：grep `lanes(`、`longFormMaxWidth(`、`symmetricInsetForCap(`
   的真实调用页，只有 1–2 处调用即说明宽屏完成度不均。
6. **性能与可访问性**：`LazyForEach`、`animateTo/transition`、`Image(` 的**零命中**本身就是强结论
   （无虚拟列表 = 全量渲染）。`ForEach` 有 key 不等于没问题，要看 key 是否混入易变状态
   （`focusActId`、`inputCategory`）导致点选即重建。

## 用仓库自带的静态尺取证

UI/设计类项目常在 `tools/` 放 `audit_*.py`。**先运行，再用输出做证据，并说明尺的口径与盲区**：

- 运行 `python3 tools/audit_x.py`（多数支持 `--probe` 反证自身可抓阳性），读文件头注释确认它查什么、
  豁免什么。典型输出可直接引用：`全部语义控件都有可及名 (pass)`、`核对结果：偏差 0 项`、
  `绕过字阶 token 0`。
- **pass 不等于合规**：只校验具名表内值的尺抓不到裸写值；只查十类语义控件的尺不覆盖可点 Row/Column。
  写结论时必须补上盲区，否则等于替代码背书。

## 输出约束

- 严格回答用户列出的编号，不写无关总结。
- 字数紧张时用短标签与行号区间，删形容词，保留判断与证据。
- 只读：不编辑、不格式化、不生成补丁；工具只用 Read/Grep/Glob（及技能工具）。

## 常见陷阱

- 只读被点名文件 → 漏掉真实阈值与静默逻辑（多在 page 层）。
- 把注释当事实 → 头注释常描述旧口径。
- 用 `find`/`ls` 找文件 → 改用 Glob；内容搜索用 Grep。
- 为凑字数省略证据 → 证据优先于解释。
- 把静态尺的 `pass` 当合规结论 → 先读它的口径与 SKIP 列表，再补它查不到的面。
- 只读被点名的页面 → 漏掉"唯一断点源/唯一 token 源"这类跨文件契约，以及未被消费的映射函数。
- 用注释里的"已落/已改"当事实 → 用 `rg -c` 计数与裸写值对照才可信。
- 把并行子 agent 的结论直接当已核实事实 → 尤其"未使用/失效"类断言，必须自己 grep 一遍；子 agent 常见偏差是把"只做了视觉遮挡"写成"闸门失效"。
- 相信工具摘要或 README 给的构建/测试命令 → 先找配置文件核对。例：元数据写着 `npm test`，实际仓库没有 `package.json`，真实入口是 hvigor + hypium。
- 全景报告里把"已完成"当结论 → 完成度要拆成功能面/工程面/发布面三档，缺口要落到"数据采集、平台审核、真机验收"这类具体类别，而不是笼统打百分比。
