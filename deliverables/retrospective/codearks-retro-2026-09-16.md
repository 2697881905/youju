# 任务执行复盘：错误与问题结构化总结

> **对象**：CodeArks（本次任务执行方）
> **周期**：2026-09-14 ~ 2026-09-16（生产数据清空 → 上架准备 → 圈子重做 → CodeArts 清单审核）
> **编写日期**：2026-09-16
> **文档性质**：复盘学习材料，客观中立、就事论事，聚焦可改进点

## 📌 摘要

本轮任务完成了生产数据彻底清空、服务恢复、备案合规上线、圈子体系重做、CodeArts 清单审核修复等工作，交付可用。但执行过程中出现了 **18 类真实失误**，集中在四个方向：

| 类别 | 条数 | 典型表现 | 主要代价 |
|---|---|---|---|
| 环境排查与验证 | 7 | 把代理/管道/网络问题误判为服务故障 | 白等 7 分钟、多轮无效排查、生产服务短暂不可用 |
| 代码实现与工具使用 | 7 | SQL 漏表/漏字段、sed 分隔符冲突、编译错误 | 数据清理不完整、脚本失败、构建中断 |
| 需求理解与方案确认 | 1 | 未先确认方案就落地，两轮返工 | 圈子方案重做 3 版 |
| 部署与流程规范 | 3 | 命令链短路、部署源不稳、设备状态未确认 | 多次重复执行、提交未推送 |

**核心教训一句话**：> 90% 的失误源于「**未验证就下结论**」——未验证进程真实状态、未验证响应来源、未验证文件已存在、未验证设备在线。验证成本远低于误判后的返工成本。

## 一、环境排查与验证（7 条）

### 1.1 把「本地代理劫持」误判为「生产正常」

| 项 | 内容 |
|---|---|
| **表现** | 在 Mac 上 `curl https://api.youju.chat/v1/posts` 返回 200 且响应体含真实帖子数据，据此判断"生产服务正常、生产可连通" |
| **背景** | 需要确认生产环境状态，本地后端同时在运行 |
| **根因** | 请求被本地 Clash（TUN 模式）劫持到了**本地后端**——响应头 `remote_ip=127.0.0.1` 已暴露异常但未警觉；`--noproxy '*'` 也绕不过 TUN 代理；未用响应特征（Server 版本、数据内容是否为本地测试数据）交叉验证 |
| **影响** | 基于错误结论推进后续判断，直到服务器上复查才发现"生产后端其实没在目标机器上"，多花了大量排查轮次 |
| **改进** | ① 验证远程服务时必须**交叉验证**：`curl -w remote_ip` + `Server` 响应头 + 响应体特征（如是否为本地才有的测试数据）；② 涉及生产判定时**优先在服务器本机执行**，而非从开发机推断；③ 对代理环境保持怀疑，看到 `remote_ip=127.0.0.1` 立即警觉 |

### 1.2 后台任务 `| head -N` 杀掉后端进程，误以为服务在跑

| 项 | 内容 |
|---|---|
| **表现** | 用 `npm run dev | head -8` 启动本地后端，日志攒满 8 行后 `head` 退出、管道写端收到 SIGPIPE，**node 进程被杀**，但后台任务壳仍显示 "running"（7 分钟），据此认为服务正常 |
| **背景** | 需要本地后端常驻供真机联调 |
| **根因** | 对 shell 管道与后台任务语义理解不足：`head -N` 读满退出会终止上游；未用真实监听状态（而非任务状态）判断服务存活 |
| **影响** | 反复 `curl` 得到 000，误以为是防火墙/网络问题，多轮无效排查 |
| **改进** | ① 后台常驻服务**禁止使用 `| head -N`**（需要截断输出用 `>` 写文件或交给任务系统）；② 判断服务存活用 `lsof -nP -iTCP:<port> -sTCP:LISTEN` 或 `curl` 实际响应，不依赖任务状态 |

### 1.3 沙箱内 curl 结果被误读

| 项 | 内容 |
|---|---|
| **表现** | 在沙箱执行 `curl` 得到 502 / 000，判断"后端挂了"；实际是沙箱代理拦截所致，加 `dangerouslyDisableSandbox` 后正常 |
| **背景** | 频繁在本地与服务器间验证服务 |
| **根因** | 未区分"命令执行环境"与"真实网络可达性"：沙箱有独立网络代理层 |
| **影响** | 一次误判后端死亡并重启了后端 |
| **改进** | 涉及端口连通性判断时，**统一在非沙箱环境执行**，或先用一个已知正常的目标做对照测试 |

### 1.4 Bash 工作目录漂移 + 路径层级缺失，导致多轮空跑

| 项 | 内容 |
|---|---|
| **表现** | 连续 3 轮 grep 全部 "No such file"：① `cd` 后仍用带前缀的相对路径；② 漏了 `ets/` 层级（`entry/src/main/pages/...` 应为 `entry/src/main/ets/pages/...`）；③ 依赖持久 cwd 但命令未重置 |
| **背景** | 批量核实代码清单时 |
| **根因** | 未使用绝对路径；未在执行前验证路径存在（如 `ls` 一次） |
| **影响** | 浪费 3~4 轮工具调用，且一度得到"0 个文件无 onError"的**假阴性**结论（差点误判条目失效） |
| **改进** | ① 批量脚本统一用**绝对路径**（`P=/abs/path` 变量）；② 批量 grep 前先 `ls` 确认路径；③ **对"0 结果"保持怀疑**，先用正向模式（如 grep 一个确定存在的关键字）验证 grep 本身有效 |

### 1.5 未确认设备在线就下发 hdc 命令

| 项 | 内容 |
|---|---|
| **表现** | 真机从 `10.116.97.50:39095` 换到 `192.168.2.3:45015`（用户换网络），未先查设备列表就发安装/点击命令，报 "Device not found" |
| **背景** | 构建后装机验证 |
| **根因** | 未在执行前 `hdc list targets` 确认设备在线与 connect-key |
| **影响** | 装机与验证链路中断，需重连后重试 |
| **改进** | hdc 操作前固定先跑 `hdc list targets`；设备 key 变化是常态（无线调试端口每次可能变），不写死 |

### 1.6 端口转发方案反复碰壁后才切换

| 项 | 内容 |
|---|---|
| **表现** | `hdc rport tcp:3000 tcp:3000` 反复报 "TCP Port listen failed at 3000"，仍重试多次；改用 LAN IP 后又发现被 **macOS 防火墙拦入站**（本机通、真机不通），再次回退 |
| **背景** | 真机连本地后端联调 |
| **根因** | 对两个方案的前置条件认识不足：rport 与主机端口占用冲突；LAN 方案受系统防火墙限制；未提前准备验证手段 |
| **影响** | 联调环境迟迟不通，多轮试错 |
| **改进** | ① 方案选择前先明确前置条件（端口是否被占、防火墙状态）；② **准备快速验证手段**（真机侧 ping/连接测试），失败立刻切换备选，不原地重试超过 2 次；③ 结论沉淀：本项目最终以 `127.0.0.1 + rport` 为主方案 |

### 1.7 SSH 不可用的情况下仍多次尝试

| 项 | 内容 |
|---|---|
| **表现** | 项目记忆已记录"SSH 密钥不被接受"，仍尝试连接生产服务器并失败 |
| **背景** | 希望代为执行生产操作 |
| **根因** | 未先确认凭据可用性就动手；对"哪些操作必须由用户执行"缺乏前置判断 |
| **影响** | 少量无效轮次；生产操作仍需用户执行 |
| **改进** | 涉及远程主机操作时，先确认凭据；不可达时**第一时间切换为"给命令让用户执行"**模式并说明原因，避免重复尝试 |

## 二、代码实现与工具使用（7 条）

### 2.1 清空脚本漏删 `Follow` 表

| 项 | 内容 |
|---|---|
| **表现** | 首版清空 SQL 的注释里列了 `Follow`，但 DELETE 语句漏写；执行后校验发现 `Follow=2`（残留） |
| **背景** | 编写 25 张表的全量清空脚本 |
| **根因** | 表清单与语句未做**机械对齐**；未逐表比对"schema 表数 vs 脚本 DELETE 数" |
| **影响** | 数据清理不完整（若未校验则残留孤岛数据） |
| **改进** | ① 脚本编写后用程序核对：`schema model 数 - 保留表数 = DELETE 语句数`；② 清空脚本**必须内建逐表 COUNT 校验**，以校验结果而非"没报错"作为成功标准 |

### 2.2 清空脚本写入非法时间戳

| 项 | 内容 |
|---|---|
| **表现** | `INSERT IGNORE INTO MediaDeletionTask (key) SELECT ...` 只给了 `key`，而 `updatedAt` 是 NOT NULL **且无 DB 默认值**（Prisma `@updatedAt` 由应用层维护）→ 写入 `0000-00-00` → 后端读取抛 `invalid datetime` 错误，**31 个 COS 媒体清理任务卡住** |
| **背景** | 删除帖子前把媒体 key 登记进删除队列 |
| **根因** | 手工 INSERT 到 Prisma 管理的表时，未检查各列的 DB 层默认值；混用了"应用层维护"与"数据库默认"两种时序机制 |
| **影响** | 定时任务持续报错、COS 旧图片未能清理（存储成本与隐私残留） |
| **改进** | ① 对 Prisma 表做手工写入前，先看 schema 确认 `createdAt/updatedAt` 是否有 DB 默认；**无默认时必须显式赋值**；② 写入后立刻用查询校验（`WHERE YEAR(col) < 1970 OR col IS NULL`） |

### 2.3 校验语句漏判 NULL，误以为数据已修复

| 项 | 内容 |
|---|---|
| **表现** | 用 `WHERE YEAR(updatedAt) < 1970` 校验，`YEAR(NULL)` 返回 NULL 不匹配 → 显示 `bad_rows=0`，实际可能仍有非法值（靠无条件 UPDATE 兜住） |
| **背景** | 修复非法时间戳后的验证 |
| **根因** | 校验条件未覆盖 NULL 分支 |
| **影响** | 校验结论不可信（好在补救动作是无条件更新，未留隐患） |
| **改进** | 校验条件写成 `WHERE col IS NULL OR YEAR(col) < 1970`；修复动作优先选**无条件覆盖**这类确定性操作 |

### 2.4 sed 分隔符与内容冲突导致命令失败

| 项 | 内容 |
|---|---|
| **表现** | `sed -i 's#</body>#<p style="...color:#999;">...#'` 报错 `unknown command: '"'`——内容里的 `#999` 被当作分隔符 |
| **背景** | 在服务器上用 sed 插入备案条 |
| **根因** | 未检查替换内容是否包含所选分隔符 |
| **影响** | 命令失败，需改用 heredoc 方案 |
| **改进** | ① 分隔符选内容中**绝对不出现**的字符（优先 `|` 或 `@`），插入前先扫一遍内容；② 复杂/多行/含特殊字符的内容**直接用 heredoc 写文件**，不用 sed |

### 2.5 grep 模式与实际内容不一致，两次误判

| 项 | 内容 |
|---|---|
| **表现** | 实际写入是 `position: fixed`（冒号后带空格），校验时用 `position:fixed`（无空格）→ 得到 0，误判"部署未生效/提交内容不对"，额外排查数轮；同类问题还发生在 `git show <commit>:<file>` 的内容校验 |
| **背景** | 校验网页样式与提交内容是否生效 |
| **根因** | 校验模式凭记忆编写，未与"实际写入内容"逐字符比对 |
| **影响** | 两轮误判与返工排查 |
| **改进** | 校验前先**取一小段实际内容**确认格式（空格、大小写、标点），再据此写匹配模式；对"0 结果"先怀疑模式本身 |

### 2.6 修复引入编译错误（2 处）

| 项 | 内容 |
|---|---|
| **表现** | ① `.catch((e) => {...})` 触发 `arkts-no-any-unknown`（Promise catch 回调参数需显式类型，这与 try-catch 的 `catch(e)` 规则不同）；② 新增 `aboutToDisappear()` 时未发现文件**已存在同名方法**（清理 cdTimer），触发 `Duplicate function implementation` |
| **背景** | 补日志与定时器清理修复 |
| **根因** | ① ArkTS 严格模式细节掌握不全（两类 catch 规则差异）；② **插入方法前未检查目标文件是否已存在同名成员**（此前 grep "aboutToDisappear" 因路径问题漏检） |
| **影响** | 构建失败 2 次（好在每次都立即修复） |
| **改进** | ① 改动后**立即编译验证**，不等批量改完；② 新增类成员前先 grep 同类声明（用绝对路径、注意层级）；③ 沉淀规则：`.catch((e: Error) => ...)` 必须带类型 |

### 2.7 多会话并发编辑导致改动被覆盖

| 项 | 内容 |
|---|---|
| **表现** | 在改 `CircleTab/tagIcons/seed` 的同时，另一会话也在改这些文件（加了版权行），保存时**把我的 style 块覆盖掉**，导致提交内容缺失、误判"提交有问题" |
| **背景** | 圈子方案迭代与用户在途改版并行 |
| **根因** | 未意识到同一工作树存在并发编辑方；改完未及时提交 |
| **影响** | 一次改动丢失需重做；一次误判排查 |
| **改进** | ① 发现工作树有"非本会话产生的在途改动"时**先提示用户**并约定修改边界；② 关键改动**改完即提交**（缩短暴露窗口）；③ 提交前用 `git show HEAD:<file>` 校验实际入库内容 |

## 四、部署与流程规范（3 条）

### 4.1 命令链 `&&` 短路导致"提交成功但未推送"

| 项 | 内容 |
|---|---|
| **表现** | 多次出现 `... && git commit ... && git push ...`：前序命令（如 SQL 校验返回非 0）导致 push 未执行，输出显示"领先 N 个提交"但远端未更新，需二次 push |
| **背景** | 修复后提交流程 |
| **根因** | 把"验证类命令"与"提交推送"串在一条 `&&` 链上，前序非 0 即中断 |
| **影响** | 多次重复推送操作，一度误以为已推送 |
| **改进** | ① 验证与提交**分开执行**（验证失败先处理，不进提交）；② 提交推送后用 `git log -1 origin/main` **确认远端 HEAD**，不以"没有报错"为准 |

### 4.2 部署源可用性未预验证

| 项 | 内容 |
|---|---|
| **表现** | 依赖 `raw.githubusercontent.com` / `cdn.jsdelivr.net` 下发脚本与配置，多次出现 Connection reset、空响应、CDN 缓存延迟（新 commit 拉不到） |
| **背景** | 生产静态文件与 SQL 下发 |
| **根因** | 对跨境网络/CDN 同步延迟的稳定性预判不足；未准备零依赖方案 |
| **影响** | 多次下载失败、文件内容不完整（curl 中断会留下半截文件） |
| **改进** | ① **首选 heredoc 直写服务器文件**（零网络依赖，本轮最终验证最稳）；② 必须用远程源时：下载后**校验字节数/行数**，不完整即重试；③ 用 commit hash 固定引用避免 CDN 缓存 |

### 4.3 多行粘贴场景下命令被吞

| 项 | 内容 |
|---|---|
| **表现** | 给用户的"两行命令"（docker cp + docker exec）粘贴后只执行了第一行，第二行无输出；用户侧看不出失败（无报错） |
| **背景** | 生产 SQL 部署 |
| **根因** | 未提供"执行后必有可验证输出"的设计；多行命令在终端粘贴存在被吞风险 |
| **影响** | 误以为已执行，实际数据未变更；需二次执行 |
| **改进** | ① 关键操作**一次只给一条命令**，并附带"预期输出"；② 用户无输出时**立即要求跑验证查询**确认状态；③ 危险/关键操作默认要求"执行后回报输出" |

## 五、测试与验证覆盖（补充观察）

### 5.1 面向用户的错误文案含开发细节，发现偏晚

| 项 | 内容 |
|---|---|
| **表现** | 后端不可达时界面显示"请确认后端已启动且 hdc rport 已建立"——属开发期文案，直到用户真机遇到才发现 |
| **背景** | 历史遗留（非本轮引入），但本轮才暴露 |
| **根因** | 异常路径的 UI 文案未纳入提审检查清单；真机异常场景（断网/后端挂）未做专项遍历 |
| **影响** | 若随发布包上架，审核员可能看到内部技术细节 |
| **改进** | ① 提审前增加"**异常态文案专项**"：断网、超时、401、404、空数据逐一在真机触发并截图；② 建立"用户可见文案不得含技术术语/rport/接口/环境信息"的检查项 |

### 5.2 真机验证受设备在线状态制约

| 项 | 内容 |
|---|---|
| **表现** | 圈子定稿后真机掉线（设备列表为空），最终未能给出真机截图，改为数据层+编译验证 |
| **背景** | 定稿效果确认 |
| **根因** | 验证强依赖单一物理设备，无备选（模拟器未就绪） |
| **影响** | 视觉确认延后到设备重连 |
| **改进** | 关键视觉改动准备**双通道验证**（真机 + 模拟器/预览器）；设备不可用时明确告知"待验证项"，不以"代码已提交"代替"效果已确认" |

## 🧭 通用改进原则（跨类别）

1. **未验证不下结论**：进程存活看监听端口、服务状态看真实响应、数据变更看查询结果、提交生效看远端 HEAD。
2. **破坏性操作三件套**：先备份 → 执行 → **用独立查询校验结果**（不以"无报错"为准）。
3. **主观需求先对齐**：命名/文案/视觉类改动，先给方案与差异对照，确认后再落地。
4. **小步快验**：改动后立刻编译；关键修复单独提交，缩短并发冲突窗口。
5. **命令设计以"可验证"为目标**：一次一条、预期输出明确、关键操作要求回报。
6. **沉淀即资产**：每一类失误在收尾时写入项目记忆（含正确做法），避免同类问题二次发生。

1. **CodeArts 扫描元数据**：扫描时间、代码版本（commit）、扫描范围与规则集——用于准确判断"失效条目"是工具落后还是分支差异。
