# 有据 × 竞品横向对比分析（小红书 / 抖音 / 微博 / 微信）

> 分析日期：2026-09-08 ｜ 版本：v1.0
> 分析基准：代码库实测（backend/src/routes、prisma/schema.prisma、entry/src/main/ets）+ 真机走查 + 竞品公开产品观察
> 定位：战略级差距清单与实施路线，供 P0 立项与版本规划参考；文档内的每项均可在后续拆分为独立 PRD。

## 一、分析说明

### 1.1 目的
回答三个问题：
1. 我们**缺什么**——相比成熟平台，哪些关键功能缺失导致用户不得不去竞品；
2. 我们**弱什么**——已有能力在体验/交互/性能/算法/生态上距标杆的差距；
3. 先做**什么**——按「核心缺口 > 重要优化 > 锦上添花」给出可落地、可排期、可验收的路线。

### 1.2 判断标准（每条建议据此评级）
| 维度 | 判断标准 | 证据来源 |
|---|---|---|
| 用户价值 | 是否直接影响「新用户留下来 / 老用户回访 / 创作者愿意发」 | 功能使用频次、竞品留存杠杆 |
| 竞争差距 | 与所对标平台的差距是「没有」(0→1) 还是「差」(1→N) | 代码里的功能是否存在 |
| 实现成本 | 前端/后端/算法/运营投入的相对量级（S/M/L，1-2 周/1-2 月/季度级） | 代码复杂度、可复用度 |
| 增长杠杆 | 对 DAU/发布渗透率/播放时长/私信打开率等北极星指标的撬动 | 行业惯例 + 本产品漏斗 |
| 合规风险 | 是否涉及内容安全、未成年保护、隐私红线（本项目已有强审核诉求） | 既有审核体系覆盖度 |

评级结果：同时满足「用户价值高 + 竞争差距大（缺失）+ 成本可控」→ 核心缺口 P0；满足两项 → 重要优化 P1；单项或锦上添花 → P2。

### 1.3 对比维度范围
- **本次覆盖**：内容发布与消费、信息分发（推荐/搜索/热榜）、社交关系与互动（关注/点赞/评论/收藏/私信）、创作者工具与激励、通知与触达、内容安全与审核、账号与隐私、性能体验。
- **本次不覆盖**（超出"功能对比"范畴，另行评估）：商业化广告系统、直播电商交易、小程序/跨端矩阵、海外本地化、视觉设计语言（见独立设计审查）。

### 1.4 交付物结构
本报告 = **战略层**（差距清单 + 优先级 + 路线图）。每项建议给出：现状证据 → 差距 → 目标 → 技术方案 → 涉及模块 → 迭代阶段 → 验收指标。战术层（每功能的详细 PRD/技术设计）在立项后按本报告「后续行动」单独产出。

## 三、竞品标杆拆解（各取所长）

| 平台 | 最值得对标的能力 | 我们的对应差距 |

## 四、核心缺口（P0）——缺失的关键功能

> 共 5 项，均为「竞品标配而我们有据缺失」，直接影响增长与留存。

### P0-1 个性化推荐与热榜算法（分发生命线）
- **现状证据**：`postService.ts:66` 明确注释「recommend（P1）初期用简单规则：回退到最新」；`hot` 仅按 upCount 类字段排序，无时间衰减与互动质量加权；无曝光去重/多样性控制；无 dislike 反馈闭环（已建 `Dislike` 表但仅用于过滤作者）。
- **竞品差距**：抖音/小红书推荐 = 兴趣召回 + 协同过滤 + 实时反馈循环；微博热榜 = 关键词热度 + 时效衰减 + 运营干预。
- **目标**：推荐流从「按时间倒序」升级为「有冷启动规则、有反馈闭环、可运营干预」的 v0.1 推荐管线。
- **技术方案**：
  1. 第一版（阶段 1）：**规则权重打分**——`score = w1·(upCount加权) + w2·(评论+收藏) + w3·(新鲜度指数衰减) + w4·(作者健康度)`，PostgreSQL 函数或服务层实现；新增 `EXPOSE` 埋点表并支持 **dislike/不感兴趣反馈**（已有 Dislike 表复用）。
  2. 第二版（阶段 2）：**标签偏好向量**——用户对 tag 的点击/互动频次 ⇒ 构建 tag 权重，推荐流按 `Σ tagWeight·交互正反馈` 排序；用 `UserFollowTag` + 新增 `PostImpression` 表支撑。
  3. 第三版（阶段 3）：引入向量召回（pgvector/开源 emb）与 AB 实验框架。
  4. 热榜：仿微博模型 `hotScore = f(互动数, 作者粉丝基数, 时效衰减 e^{-λΔt})`，配合运营人工置顶（管理后台已有雏形）。
- **涉及模块**：backend `postService.ts`、新 `recommend` 服务、`posts.ts`、管理后台；前端首页推荐流。
- **迭代阶段**：阶段 1（P0）；阶段 2（P1 增强）；阶段 3（P2）。
- **验收指标**：推荐流人均浏览时长 ↑、次留/7留 ↑、dislike 后同源内容不再出现（>95%）、热榜点进率。

### P0-2 搜索能力升级（从「查得到」到「搜得准」）
- **现状证据**：`search.ts` 仅 41 行，keyword 直接匹配（LIKE/包含），无相关度排序、无筛选、无联想、无结果聚合；无搜索历史清理/推荐。
- **竞品差距**：小红书搜索 = 综合（笔记+用户+话题）tab、相关度+时效混合排序；微博 = 搜索热词与话题聚合。
- **目标**：关键词搜索提升到「相关度 + 时效」混合排序，并具备基础筛选与联想。
- **技术方案**：
  1. 阶段 1：相关度计算——`标题权重 > 正文权重 > 标签权重` 的全文检索（PG 全文索引 `tsvector`/`pg_trgm`），`ORDER BY 相关性 × 热度 × 新鲜度`；按标签/体裁筛选参数化。
  2. 阶段 2：搜索联想词（基于 `SearchHistory` + 热词表）、搜索结果聚合分组（帖子/用户/圈子）、"热门搜索"运营词位。
  3. 阶段 3：错误纠正与同义词表、ES/Meilisearch 引入（数据量大后）。
- **涉及模块**：backend `search.ts`、`SearchHistory` 模型扩展；前端搜索面板。
- **迭代阶段**：阶段 1（P0）；阶段 2（P1）。
- **验收指标**：搜索→内容点击率、搜索零结果率 ↓、搜索带动 DAU 占比。

### P0-3 私信 IM 完整化（关系留存阵地）
- **现状证据**：`Message` 支持 text/image/video、布尔 `read`、`recalledAt` 撤回；无已读回执细节（对方是否已读的感知）、无"正在输入"、无文件/语音、无群聊、无消息收发性能保障（无分页性能测试）。
- **竞品差距**：微信 IM = 已读回执/多端同步/语音/文件/群聊/表情包；抖音私信 = 卡片消息（作品/商品）/表情互动。
- **目标**：私信从「能聊」升级到「聊天有反馈、内容可富化、消息可管理」。
- **技术方案**：
  1. 阶段 1：**已读回执体验**（`read` 已有，补"对方已读"UI + 会话已读时间戳）、**消息分页性能**（`receiverId, createdAt` 索引已建，验证滑动加载）、**消息类型扩展**（文件上传复用 media.ts + 类型枚举扩展）。
  2. 阶段 2：语音消息（录音 + COS + 播放态）、图片长按操作（保存/转发）、会话置顶/免打扰（`MessageDeletion` 已体现删除语义，可扩展 `ConversationSetting`）。
  3. 阶段 3：群聊（`Conversation` 表引入 + 成员表 + 群公告）；消息推送打通（见 P0-5）。
- **涉及模块**：backend `messages.ts`、`Message`/`MessageDeletion` 扩展、media.ts；前端 `ChatPage.ets`、`MessagePage.ets`。
- **迭代阶段**：阶段 1（P0）；阶段 2（P1）；阶段 3（P2）。
- **验收指标**：私信日活打开率、消息发送成功率、会话留存。

### P0-4 创作者工具与成长体系（内容供给侧引擎）
- **现状证据**：创作者仅有「我的发布/草稿/废纸篓」；无数据面板（阅读量/互动趋势/粉丝画像）、无内容合集/连载、无 @提及、无话题标签、无创作激励/等级。
- **竞品差距**：小红书笔记分析 + 合集；抖音创作者中心（数据/任务/收益）；微博超话与粉丝互动工具。
- **目标**：给创作者「发完看得见数据 + 内容能沉淀成专辑 + 有成长获得感」。
- **技术方案**：
  1. 阶段 1：**互动数据面板**——`Post` 已有 upCount/bookmarkCount/commentCount，新增 `views` 点击数（前端上报 EXPO），「我的发布」列表携带 vv/互动/趋势曲；**@ 提及**（解析 `@昵称` → 通知）与**话题标签**（`#话题#` → 均统一到现有 Tag 体系）。
  2. 阶段 2：**合集/连载**——新 `Collection`/`CollectionPost` 表，个人主页作品集布局；**创作者等级**（发帖量/互动质量 → 等级徽章，复用现有徽章/身份体系）。
  3. 阶段 3：创作任务（新手引导发帖任务）、可选的流量激励实验。
- **涉及模块**：backend `posts.ts`/`users.ts` 扩展 + 新 collection 路由；前端 `ProfilePage.ets`/`UserProfilePage.ets`/`DetailPage.ets` 等。
- **迭代阶段**：阶段 1（P0 面板 + @ + 话题）；阶段 2（合集 + 等级）。
- **验收指标**：月发布用户占比、人均月发布数、创作者 30 日留存、带话题内容占比。

### P0-5 推送触达闭环（消息到达中枢）
- **现状证据**：`push.ts` 仅提供 Token 注册/幂等管理，**无发送实现**（未见厂商推送通道调用）；通知全靠 App 内轮询（Index `refreshUnread`）。
- **竞品差距**：微信/微博/小红书均具备系统级离线推送，是留存与"回来的理由"。
- **目标**：关键事件（新私信/新赞/新关注/审核结果）可离在线推送。
- **技术方案**：
  1. 阶段 1：接 **HMS Push（华为推送服务）**——`push.ts` 扩展 `send` 调用（服务端用 AccessToken 发送到 PushToken 表）；事件源：私信、点赞/收藏/关注、审核完成、举报处理；限额与频控（防打扰）。
  2. 阶段 2：推送偏好精细化管理（复用 `NotificationPreference`）、Silent Push 冷启动刷新、已读后推送撤回（可选）。
  3. 前置依赖：HMS Push 依赖华为开发者账号能力（与 Account Kit 同域，已有集成基础）。
- **涉及模块**：backend `push.ts` 发送扩展、`notifications.ts` 事件钩子；前端 `Index.ets` 启动注册。
- **迭代阶段**：阶段 1（P0）。
- **验收指标**：推送打开率、推送唤起 DAU 占比、通知点击→目标页准确率。
